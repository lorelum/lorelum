The `lore` CLI defaults to complete, readable text on stdout, including Help and version. It is a visual representation of the command's public `data`, not a summary: source locators, IDs, state, progress, diagnostics, and metadata remain visible. Agents read this default text directly. Use `--json` only to diagnose an unexpected result, inspect protocol details, or let a script or CI job programmatically parse the complete one-line JSON envelope. Diagnostics and progress go to stderr; default command failures also go to stderr and include a local `diagnostics.traceId` for that original invocation.

## Commands

| Command | Purpose |
| --- | --- |
| [query](./reference/query) | Retrieve Practice summaries by task and moment. |
| [get](./reference/get) | Read an installed Practice in full. |
| [pack](./reference/packs) | Install, list, update, and remove Packs. |
| [index](./reference/indexing) | Inspect, build, and rebuild the semantic index. |
| [model](./reference/model) | Inspect, load, and unload the embedding model. |
| [backend](./reference/backend) | Start, inspect, and stop the local service. |
| `logs` | View managed local logs by source, level, or trace; `logs prune` removes only expired Lorelum log files. |
| `feedback draft` | Create a local reviewable bug or improvement draft; it never submits an Issue or uploads diagnostics. |
| [validate, format, i18n sync](./reference/authoring) | Validate Pack content and maintain localization. |
| `describe` | Return command capabilities and schemas. |

## Discover the installed contract

```sh
lore describe --json
lore describe query --json
lore describe index.build --json
lore --help --json
lore --version --json
```

`describe` returns arguments, options, result schemas, error codes, and exit codes. Use dotted identifiers for nested commands: `index.build` describes `lore index build`.

Use the installed schema when automating against a particular release. Alpha versions may change command contracts.

## Global options

| Option | Purpose |
| --- | --- |
| `--store-root <path>` | Select the Store used by Pack, query, get, and index commands. |
| `--debug` | Record debug-level local logs for this invocation without changing configuration. |
| `--log-level <level>` | Set stderr diagnostic verbosity; default `error`. |
| `--json` | Return the complete one-line JSON protocol envelope. |
| `--help`, `-h` | Show readable Help; add `--json` for capability data. |
| `--version`, `-V` | Show tool/protocol version; add `--json` for its envelope. |

Relative Store paths resolve from the current working directory. Use the same root across related commands:

```sh
lore --store-root /path/to/store pack list
lore --store-root /path/to/store query "reviewing the scope of a small UI change"
lore --store-root /path/to/store query "reviewing the scope of a small UI change" --json
```

Model configuration and Backend runtime remain user-level. See [Configuration](./configuration).

Set `logging.level: debug` in `~/.lorelum/config.yaml` for persistent release/Hook debugging. `lore --debug` also carries its one-invocation detail override to the associated authenticated Backend request and lifecycle; it does not change the daemon's global level or any concurrent request. This is separate from `--log-level`, which only changes stderr presentation.

## Local logs

Every normal text failure prints `diagnostics.traceId`; a `--json` response carries the same field in its envelope. Copy that ID to inspect the original invocation without reading Backend-private files directly:

```sh
lore logs --trace-id <traceId> --limit 100
lore logs --source hook.codex --level debug
lore logs prune
```

Logs stay below `~/.lorelum/logs/`. If that location cannot be used safely and cannot be self-healed (for example it is owned by another user), the invocation writes to the designed fallback below `~/.lorelum-diagnostics/` instead, and the envelope reports the diversion through `diagnostics.logPersistence`. `lore logs` reads both locations and labels each record's origin in `locations`. With `--trace-id`, the result also carries `evidence`, which distinguishes a read that found no matching records from evidence that was never persisted, unreadable files, and truncated reads. `lore logs` does not start a Backend or model. Missing, rotated, or damaged files are reported as evidence limits instead of being silently replaced with unrelated records. Follow [Troubleshooting](./troubleshooting) for the complete trace, debug reproduction, and feedback path.

## JSON response envelope

The fields below exist only when `--json` is selected. Do not parse default text. JSON and text use the same handler result and exit code; only the envelope itself is omitted from text.

Every `--json` CLI envelope includes `protocolVersion`, `toolVersion`, `command`, `diagnostics.traceId`, and `ok`. Hooks keep their separate host envelope and do not expose this trace metadata.

| Field | Meaning |
| --- | --- |
| `protocolVersion` | Version of the JSON protocol. |
| `toolVersion` | Version of the installed CLI. |
| `command` | Identifier of the command that produced the result. |
| `diagnostics.traceId` | Local correlation ID for this invocation. It is not an auth credential or public sharing ID. |
| `diagnostics.logPersistence` | Present only when this invocation's local diagnostics deviated from the quiet path: a log-location permission repair, a diversion to the fallback location, or logs not being persisted. Includes the attempted and used paths, the failure category, and permission modes before and after any repair. |
| `ok` | Whether the invocation produced a successful command result. |
| `data` | Command-specific result on success. |
| `error.code` | Stable error identifier on failure. |
| `error.message` | Human-readable explanation on failure. |

Branch on error codes instead of parsing messages. Within a successful result, inspect command-specific state before treating asynchronous work as complete.

## Exit codes

| Code | Meaning |
| --- | --- |
| `0` | Successful result, including an accepted operation that may still be running. |
| `1` | A command-specific diagnostic or non-final result, such as query preparation or validation diagnostics. |
| `2` | Failed invocation; inspect `error.code`. |

A query with `ok: true` and `data.state: "preparing"` exits `1`. This is not an empty search result. Index commands can exit `0` after accepting work; use the returned operation ID to check completion. In default text the same state and ID remain visible; only programmatic parsers need `--json`.

The command references specify which states and exit codes each command supports.

## Local feedback drafts

When a text or `--json` CLI result identifies a reproducible problem or a useful improvement, use its `diagnostics.traceId` to create a local draft:

```sh
lore feedback draft --trace-id <traceId> --kind bug
```

The default command creates a unique `report.json` and `report.md` directory under `~/.lorelum/feedback/` unless `--output <directory>` is supplied. It keeps the retained same-trace `error`, `warn`, and `info` call chain with ordinary context, correlation IDs, and recorded Error stacks. It does not start a Backend or model, and does not make network requests, open a URL, upload data, or create an Issue. `--include-logs info` is equivalent to the default; `--include-logs debug` adds only already-written debug records and reports `debug-records-not-found` if none exist.

`--input <file|->` is an advanced path for a manually authored observation or a test fixture when no trace is available. A draft is local evidence, not a submission. If you later choose to paste content into a public Issue, that needs a separate deliberate action; remove credentials, secrets, and anything else you do not want public, but ordinary query, result, path, and stack evidence does not need blanket redaction.
