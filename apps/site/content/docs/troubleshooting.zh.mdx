## Agent 找不到 `lore`

在启动 Agent 的环境中运行 `lore --version`。如果终端中正常、Agent 中失败，检查 Agent 的 `PATH` 是否包含 `~/.local/bin`，然后重启应用。详见[安装](./installation)。

## 命令失败时先查看原始 trace

普通 CLI failure 会在 stderr 显示 code、message、recovery 和 `diagnostics.traceId`。这个 trace 属于原始调用，重试前先复制它：

```sh
lore logs --trace-id <traceId> --limit 100
```

该命令只读取已经与这次调用关联的 Lorelum 管理日志；不会启动 Backend 或模型、下载内容、重新执行 query，也不会查看其他调用。`missingEvidence` 表示保留下来的证据存在限制：文件缺失、已轮转、已损坏，或此前没有记录 debug，都不能证明另一个原因。

如果现有记录仍无法解释问题，并且你能控制安全的最小复现，再使用 `--debug`：

```sh
lore --debug query "相同的最小任务描述"
```

这次复现会产生新的 trace，不能把它的日志当作原始 failure 的现场。只有需要 protocol 字段或脚本需要 JSON envelope 时才使用 `--json`；不要为了取得原始 trace 而重跑命令。

Host Hook 的 stdout 保持宿主 raw protocol，不会附带普通 CLI diagnostics。不要从它的 stdout 解析 trace。若 Hook 问题反复出现，可设置 `logging.level: debug`，或通过宿主支持的路径复现，再有意识地检查产生的本机证据。

## 查询返回 `preparing`

这是退出码为 `1` 的成功响应：模型准备已接受，但在 CLI 的观察时间内尚未就绪。检查状态并等待加载完成：

```sh
lore model status
lore model load
```

重新运行原来的 query。如果返回 index 缺失，再检查并构建 index：

```sh
lore index status
lore index build
```

如果返回 `semantic.index-incompatible`，应运行 `lore index rebuild`。构建被接受后可能仍在后台执行，用 `lore index operation <operation-id>` 跟踪 operation ID；涉及 Store 的命令使用同一个 `--store-root`。恢复步骤见 [Index 命令](./reference/indexing)。

## 查询没有结果

运行 `lore pack list --details`，确认当前 Store 已安装目标 Pack。查询中写清任务和决策，避免只写宽泛主题；也可以用 `lore pack list <pack-name>` 浏览 Practice。

空结果、`preparing` 和错误分别表示不同状态。Agent 应先检查 JSON 结果，再决定下一步；详见 [CLI 协议](./cli)。

## 模型下载失败

查看 `error.code`，检查剩余磁盘空间，以及能否访问配置中的模型来源。解决原因后，`lore model load` 会重试并等待加载。模型路径、缓存和下载设置见 [Embedding 配置](./configuration)。

## 用 keyword 检索诊断

需要离线查找，或想确认问题是否来自模型时，可以运行：

```sh
lore query "authentication token session" --mode keyword
```

keyword 按词语匹配。解决 semantic 检索的问题后，再运行原来的自然语言 query。

## 诊断日志未保存

Lorelum 会自愈自己的日志位置：归当前用户所有、只是权限过宽的 `~/.lorelum` 会在写入前被静默收紧；无法安全修复的位置（符号链接、他人所有的目录）会让该次调用的日志改写到 `~/.lorelum-diagnostics/` 下的私有备用位置。你不应为此执行 `chmod` 或重跑任何初始化命令。

发生上述情况时，本次调用会通过 `--json` 的 `diagnostics.logPersistence`（text 输出同样事实）说明：尝试与实际使用的路径、失败类别，以及权限修复前后的 mode。宿主 Hook 只在 stderr 给出一行提示，stdout envelope 不变。

两个位置都不可用时，命令仍按原有结果和退出码完成，但该次调用的日志没有持久化。之后 `lore logs --trace-id <traceId>` 只会如实报告"未找到该 trace 的已持久化证据"，不会猜测当时的原因。本地 Backend 的同类降级由 `lore backend status` 的 `diagnostics` 字段报告，服务本身继续运行。

## 报告问题

如果它有助于说明问题，先从选定 trace 生成一份本地、可审阅的草稿：

```sh
lore feedback draft --trace-id <traceId> --kind bug
```

它只会在 `~/.lorelum/feedback/` 下创建 `report.json` 和 `report.md`，不会上传数据、打开 URL 或创建 Issue。默认就会保留已留存的同 trace `error`、`warn`、`info` 调用链：普通 query/结果 context、correlation ID、路径和已记录的 Error stack 都是有价值的本机证据。`--include-logs info` 与默认选择相同；只有需要追加此前已经记录的 debug 时才使用 `--include-logs debug`。若原调用没有 debug record，草稿会标明 `debug-records-not-found`，不会假装能补回 detail。

创建本机草稿不需要因为普通本机证据而额外确认。之后如果你决定创建 Issue 或上传材料，那是另一个明确动作；检查 credential、secret 或你不希望公开的信息即可，普通 query、结果、路径和 stack 不需要一概脱敏。

如果决定提交 Issue，请附上 `lore --version`、平台、执行的命令、返回的错误码，以及确实能帮助维护者复现的、已经审阅过的证据。安全问题请按 [SECURITY.md](https://github.com/lorelum/lorelum/blob/main/SECURITY.md) 报告。
