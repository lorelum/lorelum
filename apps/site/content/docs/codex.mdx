The Lorelum Plugin makes engineering guidance available in Codex when it can help with the task at hand.

## Before you start

Complete [Quickstart](./quickstart). The `lore` command must be available to Codex, and you need at least one installed Pack.

## Install

```sh
codex plugin marketplace add lorelum/lorelum
codex plugin add lorelum@lorelum-plugins
```

Approve the Plugin's Hook if Codex asks, then start a new task.

### Moving from an earlier alpha

If you previously installed `lorelum@lorelum`, remove it and the old marketplace source before installing the current Plugin:

```sh
codex plugin remove lorelum@lorelum
codex plugin marketplace remove lorelum
codex plugin marketplace add lorelum/lorelum
codex plugin add lorelum@lorelum-plugins
```

## Use Lorelum

In a new task, ask Codex to use Lorelum before it settles an important plan or implementation decision. For example:

```text
Use Lorelum to find guidance for this change before you finalize the plan.
```

A successful `lore get` inside a Codex shell tool records a short candidate hint for the conversation, including when a script or pipeline runs it. Non-shell tools are skipped. When a subagent starts, it may see candidate IDs, titles, and applicability hints, then decide whether to read a Practice itself. The hint is not the Practice body or evidence that the parent adopted it. The Hook does not automatically run a query or `get`, and it does not restore these hints to the main agent after compaction yet.

The existing local Backend stores the optional list at `~/.lorelum/sessions/<host>/<session-id>/practice-reads.jsonl`. The folder uses the host's session ID directly and can hold other session data separately in the future. Deleting a worktree or restarting the Backend does not remove recorded hints. The Codex shell Hook passes the session ID to commands, including local scripts and pipelines. It does not contact the Backend on every shell call; a successful `get` reports to the Backend only if it is already running. An untrusted Hook or a command that clears its environment may leave a read unrecorded; this does not change the `get` result. Check relevance with `lore get <practice-id>` before using a hint; do not treat the list as a task record or access-control boundary.

### Why environment assignments appear before a command

The `PreToolUse` Hook automatically sets `LORELUM_HOST_KEY=codex` and `LORELUM_HOST_SESSION_ID=<current session ID>` before shell commands submitted by the agent: `export` on macOS/Linux, `$env:` in native Windows PowerShell. The agent did not write those lines, and they are not login credentials. They let `lore get` in the command or its local child processes associate a candidate hint with the right conversation. The stored record contains Practice metadata such as its ID and title, the read time, and working directory—not the Practice body, conversation, or full shell command.

These variables are not injected as extra Lorelum guidance to the agent. The rewritten command may still appear in Codex tool details or records, however, and a command that prints its environment can put them in the tool result. We therefore cannot guarantee that they never appear in visible records or model context. They are only for session association; the agent does not need to use or manage them.

Codex now needs only `PreToolUse`; the Plugin no longer installs an empty `PostToolUse` Hook. If Pre is disabled, new `lore get` reads cannot be associated with the current conversation, so subagents will not receive hints for those new reads; `lore get` itself and the Pack Catalog still work. If you still see a Post Hook after updating from an older Plugin, re-review and install the current Plugin configuration. The macOS path has been verified in a real Codex session; Linux/Windows host-level inheritance and approval behavior still need validation.

## Update

```sh
codex plugin marketplace upgrade lorelum-plugins
codex plugin add lorelum@lorelum-plugins
```

Approve changed Hooks if Codex asks, then start a new task.

## Troubleshoot

If Codex does not appear to use Lorelum:

1. Confirm the Plugin is installed and enabled.
2. Confirm `lore --version` works for the Codex environment.
3. Re-approve the Hook if Codex shows it needs review.
4. Start a new task after any installation or update.

For retrieval or model problems, see [Troubleshooting](./troubleshooting).
