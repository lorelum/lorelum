---
title: query
description: 为 AI coding task 和 moment 找到合适的已安装 Practice。
---

`query` 搜索当前 query context，返回按相关性排序的 Practice 摘要。默认使用 semantic relevance；`keyword` 是明确指定的离线路径。当前目录或父目录中的有效项目 `.lorelum/` 会按父到子继承并合并；选中的 Store root 永远不是项目 layer。没有有效项目 layer（包括整条路径没有 `.lorelum/` 的普通目录）时，query 只使用 selected Store；`--no-project` 可强制该 Store-only 行为。

```sh
lore query <text> [--mode semantic|keyword|single-vector|multi-view-vector] [--top-k <n>] [--store-root <path>] [--project-root <path>] [--no-project] [--cache-root <path>] [--verbose] [--json]
```

`text` 必填，去除首尾空白后不能为空，最多 4,096 个 Unicode 码点。`--top-k` 接受 1–50 的整数，默认 5。`--mode` 可选 `semantic`（默认）、`keyword`、`single-vector` 或 `multi-view-vector`；后两者仅为本次查询选择向量方法。未知 mode 在连接 Backend 前返回 `usage.invalid`。`--store-root` 选择 Store 基础语料，`--project-root` 选择直接包含项目 `.lorelum/` 的目录，不能指向 selected Store root；`--cache-root` 选择用户级派生 cache（默认 `~/.lorelum/cache`），不会写入项目目录；`--max-wait-ms` 与 `--min-coverage-percent` 覆盖用户级等待/partial 策略，`--require-complete` 只接受完整结果。

```sh
lore query "我将为一个小型 UI 改动定义范围和验证方式"
lore query "授权边界" --top-k 10
lore query "授权边界" --mode single-vector
lore query "授权边界" --mode multi-view-vector
lore query "token session cookie" --mode keyword
```

Semantic mode 使用 [`query.retrievalMethod` 配置](../configuration#semantic-检索方法)：默认 `single-vector`，或 `multi-view-vector`（实验）。`--mode single-vector` 与 `--mode multi-view-vector` 仅为本次查询选择对应方法，无需编辑文件：例如临时体验实验方法，或在配置选择 `multi-view-vector` 时与默认方法对比。两者都会覆盖配置的方法，即使该方法值非法也不受影响，但其他配置错误仍会报告。不写配置，不改变后续 query、index 命令或安装后的同步。结果标为 `mode: semantic`，并由 `retrievalMethod` 指明实际使用的方法。下一次普通 semantic query 会重新读取配置默认，无需重启 Backend。旧的 `simple` 和 `multi-view` ID 不是别名。`--mode keyword` 忽略方法配置，不需要 Backend 或 embedding 模型。

每种方法有独立的 index。某方法首次用于当前语料时，会为该方法单独启动后台 index 构建，因此该次查询可能返回 `preparing` 或 `indexing`；重新运行同一命令，或通过 `lore index operation <operationId>` 跟踪。`lore index status` 只报告配置的方法；`lore cache status` 包含各方法的缓存 artifact。详见 [Index 命令](./indexing)。

首次 semantic query 会自动提交或加入当前语料的后台 index operation，而不是要求先运行 `lore index build`。完整结果 data 包含 `mode` 和 `results`。每项包含 `practiceId`、`title`、`stage`、`techStack`、`appliesWhen`、`severity`、`contentDigest`；将该 `practiceId` 传给 [`get`](./get)。Semantic 结果还包含 `retrievalMethod`、`profileId` 与 `coverage`：`complete` 表示完整 artifact 与当前 Practice 完全一致；`partial` 只检索已验证的 current progress rows，并报告 `indexedPracticeCount`、`totalPracticeCount` 和 `operationId`。待完成的 `preparing` 与 `indexing` 结果同样包含 `retrievalMethod`；keyword 结果不包含。默认文本仅在其不是 `single-vector` 时显示 `retrievalMethod`；`--verbose` 与 `--json` 始终包含。变更、删除、shadowed 或 ignored 的 Practice 不会从旧 artifact 泄漏。

默认 text 是决策视图：ready 结果显示每个命中的 ID、标题、stage、非空 tech stack 和适用时机，只有非默认 severity 才显示。Keyword 结果标明 mode；partial coverage 保留状态和进度计数，ProjectContext warning 仍可见。默认视图省略 digest、Profile ID 和 ready 结果的 operation ID。使用 `--verbose` 可将完整结果 data 输出为 text。`--json` 无论是否同时传入 `--verbose`，都返回完整 envelope 和 data；机器调用方应使用 JSON，不解析 text。

Ready 查询未返回 Practice 时仍是成功结果（退出码 `0`），data 会增加 `empty` 对象；默认 text 显示说明，`--verbose` 在完整 data 前保留该说明，`--json` 则包含这个对象：

```json
{
  "reason": "empty",
  "nextAction": "continue-task",
  "message": "Query completed successfully but returned no Practices (mode: keyword). No more specific cause is confirmed. Next: continue the task without Lorelum guidance. Only if important context was missing, try at most one substantive rewrite for this lookup with the decision, constraints, and technology context. If the query was already specific or the rewrite is still empty, stop querying."
}
```

`reason` 与 `nextAction` 是稳定的机器字段；程序应读取它们，不要解析 `message`。`reason: "corpus-empty"` 表示本次完整 query context 中没有可检索 Practice；其他情况为 `"empty"`，不推断具体原因，包括 keyword query 没有匹配项。说明会保留原 mode、coverage 与计数，以及 context warnings。`nextAction: "continue-task"` 表示默认无需 Lorelum guidance 继续任务，不要求一直查到有结果。只有 query 缺少重要决策、约束或技术上下文时，本次检索才可实质改写一次；query 已具体或改写后仍空就停止，后续空响应不会重置次数。已确认空 corpus 时直接继续，不建议改写。不要把成功空结果当成模型故障，也不要自动检查 status、安装来源、修改配置或切换 mode。只有用户明确怀疑缺少预期来源时，才检查已安装 Pack。只有用户或 host policy 允许且符合现有 retrieval contract 时才考虑其他 mode；`keyword` 用于明确的离线检索或 semantic runtime 诊断。使用返回的候选前，通过 [`get`](./get) 读取完整 Practice。

模型仍在准备时，data 为 `{ "state": "preparing", "preparationId": "...", "message": "..." }`，进程退出码为 `1`；查看 `lore model status`，用 `lore model load` 等待后重试。若当前 progress 尚未达到所需覆盖率，data 为 `{ "state": "indexing", "operationId": "...", "indexedPracticeCount": 50, "totalPracticeCount": 100 }`，同样退出 `1`。两者都只表示非终态；已确认的模型或 index 失败会以 typed error 和 exit `2` 返回，不会继续显示 `indexing`。等待超时不会取消 operation。

| 错误 | 处理 |
| --- | --- |
| `query.config-invalid` | 修正或删除 `~/.lorelum/config.yaml` 中非法的 `query.retrievalMethod`，使用 `single-vector` 或 `multi-view-vector`。Keyword mode 忽略该字段。 |
| `semantic.index-not-ready` | 正常 CLI 不会返回它；query 会自动创建或加入 index。 |
| `semantic.index-incompatible` | 查看 `lore index status`；必要时运行 `lore index rebuild`。 |
| `embedding.native-resource-invalid` | 重新安装包含 `native/<target>/` 的匹配完整 CLI 包；重新下载模型无效。 |
| `embedding.resource-invalid` | 查看 `lore model status --json`，修正所报告的缓存或配置模型文件，再重试 `lore model load`。 |
| `semantic.embedding-failed` 或其他 `embedding.*` | 查看 `lore model status` 和具体错误指引，再决定是否重试。 |
| `backend.build-mismatch` / `backend.protocol-mismatch` | 按完整错误消息执行 `lore backend stop --if-idle`；只有返回 `state: "stopped"` 才运行 `lore backend start`，启动成功后以相同参数重试原命令。若 stop 返回 `deferred`，保留实例与任务，说明安全拒绝，不后台重试，也不在未经用户明确同意时使用普通 stop。 |
| `query.unavailable` / `query.failed` | 检查 keyword index 与 Store 状态。 |
| `store.busy` / `store.recovery-required` | 等待 Store 操作完成或按文档执行恢复。 |
| `usage.invalid` | 修正查询文本或选项值。 |

成功退出 `0`，准备中退出 `1`，失败退出 `2`。默认 text 与 JSON error.message 使用同一完整消息；failure 保留适用的 resource 与 diagnostics，不包含 Backend 恢复策略。机器调用方按 error.code 分支，不解析 message。完整 schema 与错误允许列表见 `lore describe query`。
