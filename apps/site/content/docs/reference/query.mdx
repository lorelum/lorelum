---
title: query
description: Find the right current Practices for an AI coding task and moment.
---

`query` searches the current query context and returns ranked Practice summaries. Semantic relevance is the default; keyword mode is an explicit offline path. Valid project `.lorelum/` layers in the current directory or its ancestors are inherited and merged from parent to child; the selected Store root is never a project layer. When there is no valid project layer, including an ordinary path with no `.lorelum/`, query uses only the selected Store. Use `--no-project` to force that Store-only behavior.

The Backend is a user-level shared service. A query may reuse an instance started by another build when the Backend internal protocol is compatible; a different build ID alone does not reject the query, restart the Backend, or reload its model. The CLI envelope protocol is `2`; the Backend protocol is `4`. Only a protocol mismatch blocks the request. Use [`backend start --current-build`](./backend) when a development check must run a specific worktree build.

```sh
lore query <text> [--mode semantic|keyword|single-vector|multi-view-vector] [--top-k <n>] [--store-root <path>] [--project-root <path>] [--no-project] [--cache-root <path>] [--verbose] [--json]
```

`text` is required, must be non-empty after trimming, and is limited to 4,096 Unicode code points. `--top-k` accepts an integer from 1 to 50 and defaults to 5. `--mode` is `semantic` (default), `keyword`, `single-vector`, or `multi-view-vector`; the last two select a vector method for this query only. An unknown mode returns `usage.invalid` before contacting the Backend. `--store-root` selects Store base data; `--project-root` selects a directory directly containing a project `.lorelum/`, not the selected Store root; `--cache-root` selects user-level derived cache and never writes into the project. `--max-wait-ms` and `--min-coverage-percent` override the user-level wait and partial-result policy; `--require-complete` accepts only complete semantic results.

```sh
lore query "I am about to define scope and validation for a small UI change"
lore query "authorization boundary" --top-k 10
lore query "authorization boundary" --mode single-vector
lore query "authorization boundary" --mode multi-view-vector
lore query "token session cookie" --mode keyword
```

Semantic mode uses the [`query.retrievalMethod` configuration](../configuration#semantic-retrieval-method): `single-vector` by default, or `multi-view-vector` (experimental). `--mode single-vector` and `--mode multi-view-vector` select that method for one query without editing the file, for example to try the experiment, or to compare against the default when the configuration selects `multi-view-vector`. Either override replaces the configured method, even an invalid method value, but other configuration errors are still reported. It does not write configuration or change subsequent queries, index commands, or install synchronization. The result reports `mode: semantic`, and `retrievalMethod` names the method that served it. The next ordinary semantic query reads the configured default again, without a Backend restart. The old `simple` and `multi-view` IDs are not aliases. `--mode keyword` ignores the method setting and needs neither Backend nor the embedding model.

Each method has its own index. The first query with a method not yet used for the current corpus starts a separate background index build for that method, so it may return `preparing` or `indexing`; rerun the same command or follow `lore index operation <operationId>`. `lore index status` reports only the configured method; `lore cache status` includes the cached artifacts of every method. See [Index commands](./indexing).

The first semantic query submits or joins the background index operation for the current corpus; it does not require a preliminary `lore index build`. The complete result data has `mode` and `results`. Each result includes `practiceId`, `title`, `stage`, `techStack`, `appliesWhen`, `severity`, and `contentDigest`; pass that `practiceId` to [`get`](./get). Semantic results also include `retrievalMethod`, `profileId`, and `coverage`: `complete` means a complete artifact matches every current Practice; `partial` searches only verified current progress rows and includes `indexedPracticeCount`, `totalPracticeCount`, and `operationId`. Pending `preparing` and `indexing` results also include `retrievalMethod`; keyword results do not. Default text shows `retrievalMethod` only when it is not `single-vector`; `--verbose` and `--json` always include it. Changed, removed, shadowed, or ignored Practices never leak from an old artifact.

Default text is a decision view: ready results show each hit's ID, title, stage, non-empty tech stack, and applicability, with severity only when non-default. Keyword results identify their mode; partial coverage retains its state and progress counts, and ProjectContext warnings remain visible. The default view omits digest and Profile IDs and operation IDs for ready results. Use `--verbose` to display the complete result data as text. `--json` returns the complete envelope and data regardless of `--verbose`; machine callers should use JSON rather than parse text.

A ready query with no results is still successful (exit `0`). Its data adds an `empty` object; default text shows the explanation, `--verbose` keeps it with the full data, and `--json` includes it:

```json
{
  "reason": "empty",
  "nextAction": "finish-lookup",
  "message": "Query completed successfully but returned no Practices (mode: keyword). No more specific cause is confirmed. Next: proceed with the current decision using other available evidence. Only if important context was missing, try at most one substantive rewrite for this lookup with the decision, constraints, and technology context. If the query was already specific or the rewrite is still empty, end this lookup only. Query Lorelum normally for other topics or new decisions."
}
```

`reason` and `nextAction` are stable machine-facing fields; use them instead of parsing `message`. `reason: "corpus-empty"` means the complete current query context has no searchable Practices. Otherwise it is `"empty"`, which leaves the cause unknown, including when a keyword query has no match. The explanation keeps the original mode, coverage and counts, and context warnings. `nextAction: "finish-lookup"` ends only this lookup, not further Lorelum use for the task or session. Query Lorelum normally for other topics or new decisions. Only if important decision, constraint, or technology context was missing may you try one substantive rewrite for this lookup. If the query was already specific or the rewrite is still empty, end this lookup; another empty response does not renew the allowance. A proven empty corpus offers no rewrite suggestion, and its finding is limited to the selected context and snapshot. Do not treat a successful empty result as a model failure or automatically check status, install sources, change configuration, or switch modes. Check installed Packs only if the user explicitly suspects an expected source is missing. Use another mode only when you or the host policy allow it and the existing retrieval contract permits it; keyword mode is for explicit offline lookup or semantic-runtime diagnosis. For any returned candidate, use [`get`](./get) to read its full Practice before relying on it.

If the semantic model is still preparing, data is `{ "state": "preparing", "preparationId": "...", "message": "..." }` and the process exits `1`; check `lore model status`, wait with `lore model load`, then retry. If verified current progress has not reached the requested coverage, data is `{ "state": "indexing", "operationId": "...", "indexedPracticeCount": 50, "totalPracticeCount": 100 }` and also exits `1`. Both are non-terminal states only: a confirmed model or index failure returns its typed error with exit `2`, not `indexing`. A wait timeout does not cancel the operation.

| Error | Action |
| --- | --- |
| `query.config-invalid` | Correct or remove an invalid `query.retrievalMethod` in `~/.lorelum/config.yaml`; use `single-vector` or `multi-view-vector`. Keyword mode ignores this field. |
| `semantic.index-not-ready` | Normal CLI query does not return this; it automatically creates or joins the index operation. |
| `semantic.index-incompatible` | Inspect `lore index status`; run `lore index rebuild` when needed. |
| `embedding.native-resource-invalid` | Reinstall the matching complete CLI package, including `native/<target>/`; redownloading the model will not repair it. |
| `embedding.resource-invalid` | Inspect `lore model status --json` and correct the reported cached or configured model file before retrying `lore model load`. |
| `semantic.embedding-failed` or other `embedding.*` | Check `lore model status` and the specific error guidance before retrying. |
| `backend.protocol-mismatch` | Follow the complete error message: run `lore backend stop --if-idle`; only after `state: "stopped"`, run `lore backend start`, then retry the original command with the same arguments. If stop returns `deferred`, leave the instance and task running, report the safe refusal, and do not retry in the background or use ordinary stop without explicit user consent. A build ID difference alone is not an error. |
| `query.unavailable` / `query.failed` | Inspect the keyword index and Store state. |
| `store.busy` / `store.recovery-required` | Wait for the active Store operation or perform the documented recovery. |
| `usage.invalid` | Correct the query text or option values. |

Successful results exit `0`; preparation exits `1`; failures exit `2`. Default text and JSON error.message use the same complete message; failures retain applicable resource and diagnostics, without a Backend recovery policy. Machine callers branch on error.code rather than parsing messages. For the installed schema and complete error allowlist, run `lore describe query`.
