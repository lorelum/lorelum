---
title: Index commands
description: Inspect, build, or rebuild the current query context's semantic artifact.
---

Query starts needed index work automatically. Use these commands to inspect, explicitly build, force a rebuild, or recover the current context.

All commands accept `--store-root <path>`, `--cache-root <path>`, and `--log-level <level>`. The Store supplies base data and user-level cache holds derived artifacts; Backend and model settings also remain user-level. A directory with `.lorelum/` uses ProjectContext by default; `--no-project` uses only the Store.

```sh
lore index status
lore index build
lore index rebuild
lore index operation <operation-id>
```

## Retrieval method

Index status, build, and rebuild use the current [`query.retrievalMethod` configuration](../configuration#semantic-retrieval-method): `single-vector` by default, or `multi-view-vector` (experimental). Each command reads the selection again, even with the same running Backend; changing it does not require a restart. Invalid values return `query.config-invalid`; correct or remove the field. The old `simple` and `multi-view` IDs are not aliases.

Status reports only the selected method's artifact and progress, not work from another method. Switching methods may therefore show `missing` or `indexing` even when the previous method was `ready`. Methods keep separate cached work; switching back can reuse a compatible artifact. An operation ID accepted before a switch still refers to its original method's work.

## Build and rebuild

`build` reuses compatible artifacts and cached vectors for the selected method. It starts the Backend and prepares the model when needed. If a complete artifact already covers the current context, it can return without rebuilding. Identical final corpora using the same method join one operation; different targets queue instead of returning `backend.busy`.

`rebuild` discards reuse and builds a complete replacement. Use it when Lorelum reports an incompatible index.

Both commands can return while work continues. Follow the returned operation ID until the result is ready or failed. Disconnecting the CLI does not cancel accepted work.

## Status

`status` inspects the current context's artifact and progress without starting the Backend. It returns `state` (`missing`, `indexing`, `ready`, `stale`, or `incompatible`) and `profileId`; `indexing` also includes the operation ID and completed/total Practice counts, while `ready` includes `vectorCount`. Keep the same `--store-root` and `--cache-root` across these commands and your query.

`status` and `operation` require a running Backend and do not start it themselves. If the service is stopped, run `lore backend start` before inspecting them.

## Operations and errors

Repeated edits to one directory pursue only its newest target. Identical artifacts join one operation; different artifacts become `queued`. Disconnecting the CLI does not cancel accepted work.

After a daemon restart, an unfinished operation keeps verified progress and becomes `waiting-for-source`. The next query, build, or rebuild in the same Store or project directory reattaches safely. A confirmed failure remains terminal and returns its stable typed error rather than another pending state; the journal stores neither project absolute paths, Practice bodies, nor private exception details.

Status and accepted builds exit `0`; confirmed failures exit `2`. An accepted operation is not necessarily finished. Run `lore describe index.build` for the current schema.
