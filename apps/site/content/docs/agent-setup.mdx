Lorelum helps your coding agent find relevant engineering guidance while it works. Complete [Quickstart](./quickstart) first so the `lore` command and at least one Pack are available to the agent.

## Host capabilities

All official Plugins use the same Lorelum Skill, `lore query`, and `lore get`. Compare the individual features below; a Plugin installation does not imply that every host lifecycle feature is available.

When an agent already uses a task or plan tool, the Skill asks it to carry specific guidance from a fully read Practice into the relevant later step and check the actual work against it. For a foreseeable material decision that still needs guidance, the Skill also asks the agent to record the specific question and when to query, such as project-specific implementation constraints before coding or test boundaries before deciding verification. At that step it asks the agent to reassess whether research is still needed, read any Practice it adopts in full, and apply it when appropriate, without querying mechanically before every edit or test. If the tool cannot safely annotate an existing step, it can add a concise, step-specific check without replacing existing tasks. Tool availability and plan persistence depend on the host and session. Lorelum does not require a plan solely for reminders, and reminders do not replace reading a Practice or checking whether it applies.

The agent should inspect an existing plan before changing it, rather than initialize a replacement and reset its phases or statuses. In omp, `todo` with `op: "view"` reads the current plan; `init` replaces it. If the plan cannot be inspected or updated safely, the Skill instructs the agent to carry the guidance in working context instead.

When a fully read Practice affects an existing step, including one already in progress, the Skill asks the agent to record the specific guidance before proceeding. In omp, the agent can append the check to the existing phase without replacing the plan.

Throughout a task, the Skill instructs the agent to assess decision-specific guidance gaps during design and planning, after planning and before first coding, before designing or writing tests, before first choosing how to run them, before failure diagnosis or rework, and before an acceptance decision. It asks for this assessment even without a plan or task tool. When guidance still needs discovery, the Skill instructs the agent to run a targeted semantic `lore query`; a known exact Practice ID can be read directly with `lore get <practice-id>`, but that read does not replace a query if other relevant guidance still needs discovery. Already-read guidance can be reused while it remains applicable. A query finds candidates, not their full guidance: the agent should read each Practice it intends to use before applying it.

These are instructions to the agent, not host-enforced guarantees. An agent may miss guidance, skip a check, or change an existing plan despite the Skill's instructions; review its actions and the plan where that matters.

At each relevant decision, the Skill asks the agent to identify the question the work needs answered; a general instruction, Catalog entry, or query for a different decision does not by itself settle it. The agent should apply applicable guidance to the current work before moving on. A prerequisite check appended later in a plan should be performed before its target step; a check of completed work remains after that work.

For example, before writing tests for a payment retry change, an agent might query for timeout and concurrent retry test boundaries, then get the full text of a relevant result before designing the tests. Before choosing how to run them, it should reassess whether it needs guidance on the available test environment; if further discovery is needed, the Skill asks it to query that decision separately. It can directly get a known exact Practice ID, but still needs to query if other guidance needs discovery; previously read guidance can be reused while applicable. A later failure or acceptance decision calls for the same assessment, not an automatic repeat of the earlier query.

Cursor's Catalog arrives asynchronously and can miss the first turn; when it is absent and the current decision needs new guidance discovery, the Skill asks the agent to list installed Packs once. Reading a known exact Practice ID alone does not require a Catalog. omp's child Catalog is opt-in with `agent.subagentPackCatalog: true`, independently of read hints. Its nested task/eval children retain the originating Main's candidates, while their own reads stay in their own sessions.

Read association requires a successful `get`, an already-running Backend, and a usable session identity. The shared [shell setting](./configuration#agent-shell-session-identity) selects eligible commands; a missed record does not change `get`. Hints contain bounded historical metadata, never full Practice bodies or proof of adoption. Main compact recovery uses only the existing compact event, not an extra startup/resume delivery. See each host's guide for the available entry points and recovery behavior.

## Other agents

Agents that can execute commands can use the same CLI. Install the Skill through the host's supported mechanism. If the host uses project instructions instead, include the Skill's retrieval instructions there.

The essential behavior is to describe the task and current decision with `lore query`, read relevant results with `lore get`, and apply the guidance within its stated conditions. The Agent reads default text directly; it does not parse its layout. When a retrieved Practice contains a `resource:` link, the installed Skill explains how to resolve it from the displayed mutable current `packRoot`, read references on demand, copy assets before editing, and explicitly run a script only under task authorization. Use `--json` only to diagnose an unexpected result or inspect protocol details. See [Agent instructions](./agents) for the full execution contract.

## First use

Start a new task and tell your agent:

```text
Use Lorelum to find engineering guidance for this task before you finalize the plan.
```

The agent should use the installed guidance when it can help with a design, implementation, verification, or recovery decision.

## Session read hints

Lorelum can keep a short list of Practices read during an agent conversation. A successful `lore get` reports a candidate only when the local Backend is already running and the host integration can associate the read with a session. A host may pass its session identity to the command or use a supported activity-window fallback. The Backend keeps the list under `~/.lorelum/sessions/<host>/<session-id>/practice-reads.jsonl`; it survives a Backend restart or deletion of the original worktree. A failed or unassociated read is simply not added, and the result of `get` does not change.

An integration with a supported child-context entry can pass those candidates to a new subagent as IDs, titles, and applicability hints. omp supplies them in task/eval model requests; Codex and Claude Code use their subagent-start Hooks. The subagent decides whether to run `lore get` itself; no Practice body is injected automatically. The list may be incomplete and says only that a Practice was read, not that the parent adopted it. It is not a task log or an access-control record. Each host Plugin defines its supported integration.

Claude Code, Codex, WorkBuddy, and omp also refresh Main's candidates after compaction. The agent rereads a candidate only when it is useful to the current task. Missing candidates or an unavailable Backend do not block continuation or start the Backend merely to restore hints. Cursor and ZCode have no post-compact refresh entry; normal query/get remains available.

For hosts that can pass session identity to shell commands, the shared [Agent setting](./configuration#agent-shell-session-identity) controls which commands receive it. See each host's guide for its Hook behavior.

## If it does not work

1. Check that `lore --version` works in the environment used by the agent.
2. Check that the Skill or Plugin is installed and enabled.
3. Start a new task after installing or updating a Plugin.
4. Use [Troubleshooting](./troubleshooting) if Lorelum starts but cannot retrieve guidance.

## Update

For a file-based Skill, replace `SKILL.md` with the latest version. Update Plugins through the host's Plugin mechanism; each installation page explains the steps.
