Lorelum helps your coding agent find relevant engineering guidance while it works. Complete [Quickstart](./quickstart) first so the `lore` command and at least one Pack are available to the agent.

## Choose your agent

| Agent                         | Recommended setup                                          |
| ----------------------------- | ---------------------------------------------------------- |
| Codex                         | Install the [Lorelum Plugin](./codex).                     |
| WorkBuddy                     | Install the [Lorelum Plugin](./workbuddy).                 |
| ZCode                         | Install the [Lorelum Plugin](./zcode).                     |
| Claude Code                   | Install the [Lorelum Plugin](./claude).                    |
| Cursor                        | Install the [Lorelum Plugin](./cursor).                    |
| Another command-capable agent | Use its supported Skill mechanism or project instructions. |

## Host capabilities

All five official Plugins provide the Lorelum Skill and a SessionStart Pack Catalog. They use the same `lore query` and `lore get` CLI; the differences below concern what each host's native Hooks can pass between a session and its subagents.

| Host | SessionStart Pack Catalog | Associate successful `lore get` reads with a session | Show read candidates to a new subagent |
| --- | --- | --- | --- |
| [Codex](./codex) | Yes | Yes, through Bash `PreToolUse` | Yes, through `SubagentStart` |
| [Claude Code](./claude) | Yes | Yes, through Bash/PowerShell `PreToolUse` | Yes, through `SubagentStart` |
| [Cursor](./cursor) | Yes, but it may appear after the first turn | Yes, through Shell `preToolUse` | No; its subagent-start response cannot inject context |
| [WorkBuddy](./workbuddy) | Yes | Yes, through Bash `PreToolUse` | No; the host does not deliver `SubagentStart` Hook output to the subagent |
| [ZCode](./zcode) | Yes | Yes, through Bash `PreToolUse` | No; the host does not provide a subagent-start event |

Cursor starts its Catalog Hook without waiting; if the Catalog is not yet visible, its Skill can list installed Packs once. Read association requires a successful `get`, an already-running Backend, and a usable session identity; a missed read never changes the result of `get`. The shared [shell setting](./configuration#agent-shell-session-identity) determines which eligible commands receive identity. A recorded read is only a possibly relevant candidate, not proof that the parent adopted a Practice. Even in Codex and Claude Code, the subagent receives bounded metadata, not the full Practice body. The SessionStart Catalog is Pack metadata, not a substitute for these read-candidate hints.

## Other agents

Agents that can execute commands can use the same CLI. Install the Skill through the host's supported mechanism. If the host uses project instructions instead, include the Skill's retrieval instructions there.

The essential behavior is to describe the task and current decision with `lore query`, read relevant results with `lore get`, and apply the guidance within its stated conditions. The Agent reads default text directly; it does not parse its layout. When a retrieved Practice contains a `resource:` link, the installed Skill explains how to resolve it from the displayed mutable current `packRoot`, read references on demand, copy assets before editing, and explicitly run a script only under task authorization. Use `--json` only to diagnose an unexpected result or inspect protocol details. See [Agent instructions](./agents) for the full execution contract.

## First use

Start a new task and tell your agent:

```text
Use Lorelum to find engineering guidance for this task before you finalize the plan.
```

The agent should use the installed guidance when it can help with a design, implementation, verification, or recovery decision.

## Session read hints

Lorelum can keep a short list of Practices read during an agent conversation. A successful `lore get` reports a candidate only when the local Backend is already running and the host integration can associate the read with a session. A host may pass its session identity to the command or use a supported activity-window fallback. The Backend keeps the list under `~/.lorelum/sessions/<host>/<session-id>/practice-reads.jsonl`; it survives a Backend restart or deletion of the original worktree. A failed or unassociated read is simply not added, and the result of `get` does not change.

An integration with a subagent-start Hook can pass those candidates to a new subagent as IDs, titles, and applicability hints. The subagent decides whether to run `lore get` itself; no Practice body is injected automatically. The list may be incomplete and says only that a Practice was read, not that the parent adopted it. It is not a task log or an access-control record. This belongs to the shared Agent integration layer; each host Plugin defines which Hooks it supports.

For hosts that can pass session identity to shell commands, the shared [Agent setting](./configuration#agent-shell-session-identity) controls which commands receive it. See each host's guide for its Hook behavior.

## If it does not work

1. Check that `lore --version` works in the environment used by the agent.
2. Check that the Skill or Plugin is installed and enabled.
3. Start a new task after installing or updating a Plugin.
4. Use [Troubleshooting](./troubleshooting) if Lorelum starts but cannot retrieve guidance.

## Update

For a file-based Skill, replace `SKILL.md` with the latest version. For Codex, WorkBuddy, ZCode, Claude Code, and Cursor, update the Plugin in the host application; their installation pages explain the exact steps.
