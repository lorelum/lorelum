Lorelum 给 Codex、Cursor 这类 AI 编码助手提供工程经验。每条经验叫一个 Practice，讲的是“遇到什么情况该怎么做、为什么”，比如“给没参与讨论的 reviewer 写 PR 描述时，要把背景和决定写完整”，或者“React 服务端渲染时，同一请求里的重复查询要去重”。Agent 干活时用一句话来查，Lorelum 返回最相关的 5 条。

查找靠语义检索：把问题和每条 Practice 都转换成一个向量（embedding），向量越接近，说明意思越相近。它不要求关键词一字不差，中文问题也能找到英文写的 Practice。

这套检索大部分时候表现不错，但有一类问题它总是处理不好。

## 一个排错的例子

一个 Agent 刚修完 React 的缓存 bug，准备开 PR。它来查的是（原文是英文）：

> 我在开一个修复 React 缓存 bug 的 PR，reviewer 看不到我们之前的聊天记录，所以要把背景和决定写完整。

它想知道的是 PR 描述怎么写。检索结果的第 1 名却是一条讲 React 服务端请求去重缓存的 Practice，PR 写作那条排在第 2。

答案其实找到了，只是排序错了。整句话被转换成一个向量，“React”“缓存”这几个技术词分量很重，Agent 真正要做的事——写 PR 描述——反而被冲淡了。

## 真实任务要的不止一条答案

这个例子还算简单：只有一条该排第一的 Practice。真实的任务往往更复杂。

比如 Agent 改完一个 React 表单，提交前想做一次 code review，把顺手加的多余 state、辅助文件和包装组件删掉。对它有用的 Practice 分三种：

- **目标 Practice**：直接回答“现在该做什么”。这里是“提交前做一次减法 review，删掉这次改动用不到的东西”。
- **辅助 Practice**：不是这次任务本身，但能帮着把事做好。这里是 React 的“能从 props 算出来的值，就别再存一份 state”，review 时正好用得上，还有“选最小够用的设计”。
- **形似的 Practice**：看起来很像，其实不该用。Lorelum 里还有一条也叫“减法 review”的 Practice，讲的是给 Pack 写经验内容时怎么删减，和代码 review 是两回事。

理想的结果是：目标排第一，辅助的也在前 5 里，形似的别挤进来。技术领域该起作用，但应该是“帮忙”，而不是“抢位”。

我们定的排序原则是：先看现在要做什么，再看处在哪个阶段、涉及什么对象和约束，最后才看技术领域。同时有两个前提：不能要求作者换一种方式写 Practice，也不能要求用户查询时手动标出“这是任务”“这是背景”。

## 我们怎么测

要知道改得好不好，先得有一套测试题。我们准备了两套，用的是同一批 97 条 Practice，来自 4 个 Pack：AI 编码工作流 34 条、写 Pack 的方法 27 条、React 24 条、Issue 与 PR 写作 12 条。

**第一套：50 条问题，每条标一个目标 Practice。** 问题都是 Agent 在干活时会问的一句话，覆盖了几种典型的问法：

| 问法 | 数量 | 例子（中文为转述） |
| --- | --- | --- |
| 直接问 | 16 | 提交前，把这次改动用不到的代码和抽象删掉，哪怕它们以后可能有用。 |
| 换个说法 | 15 | 组件把 fullName 存在 state 里，每次 firstName 变了就重新算一遍，用当前的 props 把它简化掉。 |
| 多个约束混在一起 | 12 | 交接时有一个已知的迁移限制、一个可选检查没通过，下一个工程师必须知道什么？ |
| 相邻阶段 | 11 | 一行文案改动，团队却提议跑全套浏览器矩阵和压测，验证做到什么程度才合适？ |
| 容易和相邻 Practice 混淆 | 6 | 购物车数量为 0 时，页面上渲染出了一个数字 0。 |
| 任务和技术领域冲突 | 5 | 开头那条 React 缓存 PR 的问题 |
| 中文提问 | 2 | 服务端输出的时间和客户端首次渲染的时间不同，页面出现 hydration 警告，该怎么处理？ |

> 来源：第一套 50 条问题 · 一条问题可以同时属于几类

其中 6 条还标了形似的 Practice，用来检查它们会不会排到目标前面。

**第二套：40 条问题，专门考“目标 + 辅助”。** 第一套只有目标，看不出辅助 Practice 有没有被照顾到，所以我们又写了一套。分 8 类，每类 5 条：直接问、换说法、看着相关其实不该用、相邻阶段、任务和领域冲突、同一主题不同阶段、中文查英文、长句多约束。上面那个 React 表单 review 的例子就在里面。

每条问题由两个互不知情的标注 Agent 各自标出目标、辅助和不该出现的 Practice，目标以两边都认可的为准。有 34 条标出了目标，另外 6 条本来就不该命中任何 Practice，只用来检查有没有不该出现的结果混进前 5。后来我们又补了一条中文的 code review 问题，合计 35 条有目标。

两套题都给全部 97 条 Practice 打分、完整排序，所以除了看前 5，还能看到正确答案到底排第几。

## 先看清问题出在哪

用第一套题跑原来的检索，结果很清楚：50 条里有 49 条能在前 20 名找到目标 Practice，进前 5 的只有 42 条，排第一的只有 26 条。不少答案卡在第 6 到第 13 名，和第 5 名只差一点点。

也就是说，检索基本都能找到答案，问题出在排序上。

## 关键词加分：数字变好了，我们还是删了它

最直接的办法，是在向量相似度之外，再按关键词匹配程度加一点分。我们用的是搜索引擎里很常见的 BM25 算法，权重定得很小，只在两条结果分数接近时起作用。

效果立竿见影：第一套题里，进前 5 的从 42 条升到了 48 条。

但继续往下查，问题一个接一个冒出来。

最大的问题是中文。Lorelum 的 Practice 大多是英文写的，用户却常用中文提问。关键词匹配要求字面上对得上，中文问题和英文 Practice 之间根本没有共同的词。我们拿“服务端渲染”“请求级查询”“去重”去搜对应的英文 Practice，一条都没匹配上；而向量模型给这对中英文的相似度是 0.9937，几乎认定是同一个意思。

还有一些更隐蔽的问题。一个问题里有英文单词“I”（我），两条不相关的 Practice 正文里出现了“I/O”，就因为这个拿到了很高的关键词分，把正确答案挤了下去。关键词命中，不代表和要做的事相关。

为了 6 条测试问题的提升，让中文用户的体验整体变差，不划算。我们删掉了这部分，还加了一条测试，防止关键词逻辑以后被悄悄加回语义检索里。

## 换个思路：把问题和 Practice 都拆开

回头看，根子在“一句话一个向量”。不管怎么加分，只要整句话被压成一个向量，技术词和任务描述就混在一起，分不开。

所以我们改了比较的方式：问题拆成几段，Practice 也拆成几块，逐段比较之后再汇总。

问题按标点拆开，中英文标点都算。开头那个问题会被拆成三段：

1. 我在开一个修复 React 缓存 bug 的 PR
2. reviewer 看不到我们之前的聊天记录
3. 所以要把背景和决定写完整

Practice 拆成两部分。一部分是“适用场景”：标题、什么情况下适用、处在哪个阶段、常见的错误做法。这部分回答“什么时候该用这条”，技术栈字段特意没有放进来，免得“React”这类词单独决定匹配结果。另一部分是正文，按段落切开，每段带上所在的小标题，这样“除非……”“不要……”这类条件不会脱离上下文。

拆开之后，每一段各自去找最匹配的 Practice。在开发过程中单独看每一段的排名：

- 第一段里有“React 缓存”，缓存那条 Practice 排第 1，PR 写作那条只排第 10；
- 第二段讲 reviewer 看不到上下文，PR 写作那条升到第 3，缓存那条掉到第 50；
- 第三段讲把背景写完整，PR 写作那条排第 30，缓存那条排到了第 87。

缓存那条只在第一段里占优，到了后两段几乎不沾边；PR 写作那条虽然没有哪一段特别突出，但在三段里都不算差。用最终的实现在 97 条 Practice 上整体跑一遍，PR 写作那条排第 2，缓存那条从第 1 掉到了第 23。

技术词还在起作用，只是不再能单独决定结果。

## 几个小细节

真正落地时，有几处细节比预想的要费工夫。

**正文的分数怎么算。** 一条 Practice 有很多段正文，如果只看“最像的那一段”，段落多的 Practice 更容易碰巧撞上一段；如果只看所有段落的平均分，真正相关的那一段又会被稀释。最后我们两者各取一半。

**要不要惩罚背景段。** 我们一度担心背景段影响太大，在总分里额外混入“得分最低的那一段”作为惩罚。测下来，惩罚越重效果越差。它把另一类正确答案也压了下去：和要做的事很匹配、但和背景关系不大的 Practice。直接取平均已经足够，惩罚是多余的。

**中文要按字数估算长度。** 向量模型对单次输入的长度有上限，超过就报错。中文差不多一个字算一个 token，英文大约四个字母一个 token；如果按字符数来切，中文会比英文早四倍左右超出上限。所以切分时按估算的 token 数，而不是按字符数。

## 也试过一些别的办法

这期间还试过几个方向，最后都没有采用。

一个是把每段的排名合并，而不是把分数合并。它在测试里多对了 1 条，但等于换了一套排序算法，而且合并方式有好几种，选哪种做默认都说不清理由。

另一个是人工给问题标注角色，比如哪部分是要做的事、哪部分是技术背景，再按角色给不同权重。结果反而变差了。我们又做了一个对照：同样把问题切开，但不标角色，结果和标了角色一样。说明起作用的是切分本身，角色标注没有带来额外的好处。

效果最明显的，是让大模型逐条判断“这条经验现在适不适用”。只按它的判断排序，69 条测试问题里进前 5 的从 33 条升到了 54 条。不过这需要调用大模型，成本和延迟都不一样，更适合做成单独的一层服务，而不是塞进本地检索。

## 效果：目标排得更靠前了，辅助的还没跟上

下面的数字都是用现在已合入的代码、同一批 97 条 Practice 重新跑的。

**第一套题上，提升主要体现在“排第一”。**

| | 原来的整句匹配 | 分段匹配 |
| --- | --- | --- |
| 目标排第 1 | 26/50 | **33/50** |
| 目标进前 3 | 36/50 | **43/50** |
| 目标进前 5 | 42/50 | **45/50** |
| 目标进前 20 | 49/50 | 47/50 |
| 形似的排到目标前面 | 2 条 | 1 条 |

> 来源：第一套 50 条问题 · 97 条 Practice

Agent 最常看的就是前几条，所以“排第一”从 26 条到 33 条，比前 5 多出 3 条更有意义。代价是有两条原本在前 20 的答案掉了出去，它们本来就没进前 5。

**第二套题上，好坏参半。**

| | 原来的整句匹配 | 分段匹配 |
| --- | --- | --- |
| 目标进前 5 | 26/35 | 27/35 |
| 目标排第 1 | 20/35 | 17/35 |
| 辅助 Practice 进前 5 | 16/27 | 13/27 |
| 不该出现的进了前 5 | 9/41 | 7/41 |

> 来源：第二套 40 条问题 + 1 条补充 · 97 条 Practice · 辅助一项只统计标了辅助 Practice 的 27 条

分段匹配最擅长的，是技术词把任务盖住的问题。比如“开始写 React 仪表盘之前，范围该放多大，什么时候停止加东西？”，原来的检索前 6 名全是 React 的性能和渲染 Practice，目标“定范围和停止条件”排第 13；分段匹配后它排第 1，前 5 里一条 React 都没有了。长句多约束的问题也明显变好，比如一条带着“今天要上线、午饭后要录演示”的范围问题，目标从第 30 升到第 11。

但它也把一部分辅助 Practice 一起压了下去。“给服务端 action 的鉴权修复写收尾说明，哪些遗留问题必须写？”这条，原来排第 1 的是 React 的“服务端 action 要做鉴权”，目标排第 8；分段匹配后目标升到第 1，可那条 React Practice 掉到了第 15。它本来是有用的背景。

前面那个 React 表单 review 的例子，两种方式都处理得不错：原来目标排第 1，React 那条辅助排第 3；分段匹配后目标第 2，辅助第 5，形似的 Pack 减法 review 都在第 14 名以后。

一句话总结：分段匹配能更稳地把“要做的事”排到最前面，但还分不清哪些技术领域的 Practice 是在帮忙、哪些是在抢位。

## 上线：先作为可选模式

第一版实现直接把分段匹配设成了默认的检索方式。我们最后没有这样合入。

第二套题的结果说明，分段匹配在一部分问题上更好，在另一部分上会丢掉有用的辅助 Practice。用户每天依赖的是默认行为，不能换成一个还有明显短板的版本。所以第二版做了调整：默认检索保持原样，分段匹配作为可选模式提供。想试的话，查询时加一个参数就行，不用改任何配置：

```sh
lore query "当前任务" --mode multi-view-vector
```

两种方式各自维护独立的索引，互不干扰；命令行的结果里也会标明这次用的是哪种方式，方便对比。

接下来要解决的，就是让检索分得清“帮忙”和“抢位”。前面那个大模型逐条判断适用性的方向，正好对准这个问题，会作为单独的一层服务来做。

## 写在最后

这次优化最大的收获，是让我们想清楚了一件事：检索出了问题，先别急着往公式里加分数，先看是不是比较的方式出了问题。关键词加分让数字好看了一阵，但真正起作用的，是把问题和 Practice 拆开来比。

另一个体会是，测试题怎么出，决定了你能看到什么。只看目标 Practice 时，分段匹配几乎全面领先；补上辅助 Practice 之后，才看出它的短板。新方法先作为可选模式上线，比一次性替换稳妥得多。
