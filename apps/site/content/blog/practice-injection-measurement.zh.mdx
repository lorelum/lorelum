Lorelum 是我们在维护的开源项目：将工程经验组织为结构化、可检索的指导卡片，在 AI 编码 Agent 执行任务时，将与当前决策相关的卡片交付给它。这类卡片称为 Practice。产品的核心假设是：获得正确 Practice 的 Agent，能够产出质量更高的代码。

该假设的验证是一个受控实验问题：在其他条件完全一致的前提下，注入相关 Practice 是否改善 Agent 产出的代码质量。为此我们构建了一套对照测评系统，并在两个月内对它进行了三轮推翻重构：第一轮，评测将「与参考实现的相似度」误当作「Practice 被遵循」；第二轮，运行数据无法区分「执行失败」与「指导未生效」；第三轮，用于质量评分的语言模型在首次判别力校准中给出了方向相反的结果。本文按时间顺序复盘这三轮推翻重构的动因、方案与结果。全部素材与运行记录公开在 [lorelum-benchmark](https://github.com/lorelum/lorelum-benchmark) 仓库，可逐条核对。

## 为什么这个问题难以测量

首先描述一次实验运行。编码 Agent（我们使用 Pi）接收一份任务题面和一个初始代码库，自主读取代码、修改代码、运行测试，在数分钟内产出一组代码变更。实验要测的变量只有一个：运行开始前，是否注入一段与任务相关的 Practice。Practice 只描述职责边界，例如「组件只负责交互与展示，远程调用经领域操作完成，不直接依赖 HTTP 客户端」；它不包含任何项目的文件路径或函数名，因此可迁移到同类场景。

直觉的验证方式即上述两组对照。真正实施后，三个直觉假设先后被推翻。

第一个直觉是「每个条件执行一次即可」。同一条件、同一输入重复执行，一次运行可能完全符合指导的分层结构，另一次则完全偏离，这属于常态；模型不支持固定采样种子，无法保证两次采样结果一致。单次运行几乎不携带信息，结论只能依靠预先声明的重复次数来估计。

第二个直觉是「以测试即可判定优劣」。功能正确性可以由测试判定，但 Practice 改变的是结构质量。「分层更好」不是对错问题，必须先定义、再观测，而定义环节最容易引入主观偏差。

第三个直觉是「其余条件保持一致即可」。题面多一句提示、评测修改一行代码、条件的执行顺序、依赖版本——任何一处不受控的差异，都可能表现为「Practice 生效」的假象。

测评系统的全部工作，就是逐一控制这三个来源。以下按时间顺序复盘。

## 最初的测量：条件与两个错误

为执行第一次对照，我们为登录页任务准备了一套材料：题面、初始代码库，以及一张与「前端分层」相关的 Practice 卡片。从这一次起，对照即由两组扩展为三组，原因是「注入有没有用」叠加了两个假设：向 Agent 提供一段指导文本优于不提供；以及，提供**正确的**指导优于提供任意一段指导。仅比较「注入与否」验证的是前者，需要验证的是后者。因此每个任务执行三个条件：

- **baseline 组**：不注入任何内容，空白对照；
- **oracle 组**：注入与任务直接相关的 Practice，即人工选定的、与该任务最匹配的卡片（oracle 在实验设计中的含义即「已知的标准答案」）；
- **无关组**：注入一张等长、同格式、但主题无关的 Practice，例如向登录任务注入一段关于列表渲染的指导。

无关组是关键控制：只有 oracle 组同时高于 baseline 组与无关组，才能说明收益来自「指导的相关性」，而非「上下文中增加了一段文本」。三个条件之间除注入内容外全部固定：同一任务版本、同一初始代码、同一模型与提示、同一预算。

判定由评测器完成——一段自动检查脚本，在 Agent 提交后逐项验证并输出结果。设计评测的常规起点是先编写一份参考实现作为标准答案，再对照它编写检查项。第一个错误恰恰发生在这一步：检查发现，多个检查项实际来自参考实现的具体写法，例如「必须存在 `src/features/auth/loginService.ts`」「组件须导入 `./services/http` 的 `postSession`」。以这类条件判定「Practice 被遵循」并不严谨——它们检查的是布局与命名的相似度，而非指导本身的工程原则。一份职责完全等价、但将同样逻辑置于其他文件、使用其他命名的实现，会被判为失败。实验的因变量由此被替换：测量的不是「指导是否生效」，而是「与参考答案的相似度」。

第二个错误更为隐蔽：一次运行结果不佳，无法归因。以下三种性质完全不同的情况，在早期记录中属于同一种「失败」：

- 运行未执行完毕（超时、基础设施故障）；
- 任务功能本身错误；
- 功能正确，但 Practice 针对的质量维度未被观测到。

混合记录的数据无法回答任何问题。这一轮没有产生关于 Practice 本身的结论，产出的是两条教训：任务材料需要明确的信息边界，运行结果需要分维度记录。而将教训落实为规则，前提是实验可执行、成本可负担。

## 实验执行的自动化

最早的试运行依赖人工值守：准备干净工作区、发起一次 Agent 运行、等待完成、归档输出，再进入下一个条件。一个任务在三个条件下各执行三次，共九次完整运行。更严重的问题不是耗时，而是容易出错：条件与重复编号依赖人工记录，输出依赖人工收集，出错一次，整批数据即被污染。

执行随后被推向自动化。第一步是为登录页任务编写专用的本地执行脚本——一个合理的 v0，为单一任务快速建立可执行的路径。任务增多后，仓库中一度并存多条执行路径，通用执行器的提案逐条指出了它们的问题：两条会生成正式运行记录——正式记录一经生成就不可变，是对外结论的依据，诊断阶段不允许产生；一条不校验两次运行是否基于同一份材料，也无法阻止 baseline 组获取 Practice 文本；最早一条与后续结果不兼容，被明确禁止混用。

由此产生了通用执行器：新任务零代码接入，声明的条件、重复次数和输入清单直接构成执行计划。它的三项保证，每一项都对应一次已付出的代价：

- 每次运行前校验任务版本、代码快照与全部输入的指纹三者一致——证明本次运行与对照运行确实基于同一份材料，不一致则不创建工作区、不请求模型；
- Practice 文本仅经内存通道以系统提示注入，不落盘到工作区、运行日志或输出，baseline 组在物理上无法获取它；
- 单次运行异常仅隔离记录该次，不中断其余运行。

上线后我们又发现并修正了一个偏差。最早的执行器按固定顺序整批执行条件——固定顺序同样是 v0 的自然选择，但它意味着无法排除「条件差异」中混入「执行顺序差异」：例如模型服务在某段时间恰好更不稳定，而该时段全部在执行同一条件。修正方案是将执行顺序改为由种子派生的循环拉丁方：每个重复块内三个条件各执行一次，顺序随机化，计划在执行前登记、此后不再变更。统计以计划登记的运行次数为准——失败与超时的运行计入统计，不得剔除。补跑同样设有门禁：怀疑评测器异常时，允许执行三个条件各一次的最小计划以验证健康状态，但结果强制标记为「仅限诊断」，不得用于任何结论。

自动化与顺序平衡到位后，最后一类浪费是无人值守运行中的静默停滞。诊断单轮运行十余分钟，Pi 有时长时间没有输出，无法区分它是在推理、在等待网络，还是已经停止。检查发现了三个具体问题，同一天提交了五个修复：

- 超时仅终止直接子进程，残留的孙进程仍在后台运行 → 超时改为终止整棵进程树；
- 对输出管道的等待没有上限，无输出即无限等待 → 管道等待设置上限；
- 语义硬门槛检查需要在浏览器中实际运行被修改的应用，评测器依赖 vite 启动的开发服务器，该服务器未预启动时评测器会无限等待 → 预启动 vite。

另外两项修复是单次运行五分钟预算与停滞看门狗加全局时限；Pi 自带的停滞检测也随之关闭，改由我们自己的预算和看门狗接管。修复后，六个计划运行在约 22 分钟内完成，超时被记录并自动重试一次——停滞从无法区分的等待变为数据中可观测的事件。

至此，一次三条件对照从人工流程变为单条命令，失败与停滞都成为被记录的数据。实验成本降低之后，后续几轮重构才有可能。

## 任务材料：题面与 Practice 的纪律

对照之外，仍有两个位置会引入偏差：任务题面提前给出答案，或评测沿用参考实现的标准。为此，任务材料中的全部信息被划分为五类，各自承担明确职责：题面只描述目标产品行为（「登录成功显示欢迎、失败显示通用错误、提交期间防重复提交」），不写实现路径；Practice 只写职责边界与理由，不绑定文件名；语义硬门槛的检查只验证题面声明过的行为，由浏览器测试自动执行；质量信号只检查职责等价的结构证据；参考实现的路径、命名、布局仅作报告信息，不作为判定条件。

以一张合格的 Practice 卡片为例：

> 让组件聚焦交互与展示，通过领域操作调用远程能力，不直接依赖 HTTP 客户端；在 API 边界把响应翻译成领域结果，不让原始响应对象流入组件状态；组件不解释状态码。

不合格的写法则是：「在 `LoginPage.tsx` 中导入 `./services/http` 的 `postSession`，新建 `src/features/auth/loginService.ts` 处理请求。」它将单题参考实现的路径和函数名写成了指导，任何职责等价但布局不同的实现都会失败，不可迁移。

题面同样需要收敛。一个后端任务的任务卡先后修改三轮：先按开发工单的语气重写；再删除实现提示——保留提示时，题面本身已给出分层方案，Practice 不再构成差异变量；最后删除文件路径，由 Agent 自行在仓库中定位。第三轮的提交说明直接陈述了动机：使 Practice 成为唯一的区分因素（practice stays the differentiator）。

配套的约束还包括：任务版本不可变，修改任何内容即创建新版本，既有运行记录永不重写；Agent 可见材料与评测私有材料物理隔离；一次性的手工试验产物存放于被 gitignore 的 scratch 目录，明确规定不得用于支撑任何结论。至此，「差异只可能来自注入内容」成为工程事实。

## 判定规则：三个维度、探针与 judge

针对「三种失败混在一起」的问题，解法是一套固定的判定规则，将一次运行拆为三个独立维度：

| 维度       | 回答的问题                          | 是否决定任务完成 |
| ---------- | ----------------------------------- | ---------------- |
| 执行健康   | 本次运行是否正常执行完毕            | 否               |
| 语义硬门槛 | 题面声明的功能行为是否正确          | 是，唯一完成信号 |
| 质量信号   | Practice 针对的质量维度是否被观测到 | 否，仅报告       |

执行健康只依据运行自身的证据——进程退出码、输出是否完整——不允许从语义或质量结果反推；质量分数在任何情况下都不能改变任务完成状态。

「质量维度被观测到」不由人工判断。做法是将「分层正确」拆解为少数几个可以用代码验证的职责事实，每条事实交给一个探针——一段针对单一质量维度的检查脚本。以登录页任务为例，探针验证：组件中等待的是否为组件外的领域操作，而非原始 HTTP 响应；传输错误（如 401）的翻译是否发生在边界模块。探针只检查职责事实，接受任何命名和目录布局的等价实现。

探针的优势是精确，局限是覆盖面：它只能检查预先声明的事实，无法评价代码的整体质量。人工审读可以覆盖这一范围，但一次对照产生九段变更，人工判定既慢又不稳定，且判定人的预期会泄漏到结果中。因此我们引入了 judge：将题面、初始代码和提交的变更交给一个语言模型，由它按照一份评分细则对代码逐维度给出 0–100 的参考分，并为每项得分说明理由。评分细则以独立文件维护，结果记录其哈希。judge 的权限同时受到严格约束：输入只允许公开材料，任何包含条件信息、Practice 文本或私有评测材料的输入直接拒绝；每个结果必须携带 judge 模型版本及提示、细则、输入的哈希，缺失任何一项即整体判为失败；CI 中默认使用确定性 mock provider，不调用外部模型。

judge 随即在第一次判别力校准中失败。校准方法是提供三份代码——参考实现、职责等价实现、反模式实现——要求 judge 评分，合格标准是等价实现接近参考、反模式显著更低。judge v1 对参考实现给出 66 分、等价实现 80 分、反模式实现 72 分：方向相反，等价实现高于参考实现，反模式未被分离。第二次重试时校准直接中断——模型返回的 confidence 字段不是整数，解析器按规则拒绝，整轮未完成。

问题定位为两处：自动生成的评分细则对「功能正确但结构为反模式」的实现缺乏区分度；输出解析对数值字段过于严格，格式波动即导致整体失败。修复后的 v2 扩展了细则维度、对数值做容错归一，重新校准的结果为参考 90、等价 88、反模式 76，全部通过。v1 的失败证据按原样保留在仓库中。

最后是计数规则；它们先于结果陈述，是阅读下文结果的依据：

- 每项运行归为一个布尔结果——「通过」定义为语义硬门槛通过，且探针观测到目标质量维度；judge 的参考分不参与通过的判定。
- 一个条件要构成「方向性信号」，其通过次数必须**严格高于**另外两个条件；持平或更低仅具诊断意义。
- 一个**单元**（同一任务在同一条件下的全部重复）中出现执行失败的，该单元整体记为「不确定」，不参与比较。

## 目前的证据与边界

执行最完整的一轮覆盖三个任务：登录表单、资料保存、项目目录搜索，各自对应一张分层类 Practice。登录页任务的复测计划固定为每条件 6 次，另两个任务为 3 次。按上述规则统计通过次数（oracle 即相关 Practice 组，irrelevant 即无关组）：

| 任务                 | oracle | baseline | irrelevant |
| -------------------- | ------ | -------- | ---------- |
| 登录表单（6 次）     | 3      | 1        | 2          |
| 资料保存（3 次）     | 3      | 1        | 1          |
| 项目目录搜索（3 次） | 3      | 0        | 0          |

三个任务的 oracle 组均严格高于各自的两个对照组，方向一致。judge 的参考分也一致更高：oracle 组 68–100，baseline 组 48–61。分差集中在与 Practice 直接相关的维度——以资料保存任务为例，oracle 组与 baseline 组的对比为：领域委托 20 对 14（满分 20）、边界翻译 14 对 4（满分 20）、原始响应不出边界 10 对 2（满分 10）。

代码层面的差异可以直接对照。baseline 的组件直接读取传输层响应：

```tsx
import { postSession } from "./api/http";
const result = await postSession({ email, password });
if (result.status === 200) {
  setDisplayName(result.body.user.display_name);
} else {
  setError(result.body.message);
}
```

oracle 组的组件只消费领域结果，翻译发生在边界：

```ts
export type LoginResult = { ok: true; displayName: string } | { ok: false; message: string };

export async function login(email, password): Promise<LoginResult> {
  const response = await postSession({ email, password });
  if (response.status === 200) {
    return { ok: true, displayName: response.body.user.display_name };
  }
  return { ok: false, message: response.body.message };
}
```

结果有三条必须说明的边界。

第一，噪声是真实的。oracle 组存在 judge 参考分为 0 的运行，baseline 组也出现过 100 分的运行。这些数字说明的是「高质量分层出现的概率更高」，而非「注入必然正确」。登录页任务的单元中共出现两次执行失败，按前述规则，该任务整体记为「不确定」。

第二，高分不等于生效。无关组的一次运行获得 71 的参考分——交互细节完成度高——但结构问题与 baseline 相同：组件同样直接读取 `res.status`，分层收益为零，探针判定为未观测，不计入通过。judge 分数再高也无法改变这一判定，这就是「探针决定通过、judge 仅作报告」的原因。

第三，收益有明确的范围。两组都在加载状态、错误重试界面、防重复提交上失分。Practice 提升的是它指导的维度，不覆盖交互完整性。

另有一次反例值得记录。一个后端任务的三条件对照（每条件 3 次）中，oracle 组通过 1 次，无关组同样为 1 次，未严格高于对照——按规则，结论停留在「仅限诊断」。严格规则的价值正在于此：它阻止含混的数据转化为有利的叙事。

最后一层边界关于问题本身：在 Lorelum 产品中，Practice 应由检索自动挑选；上述实验中，它由人工选定。因此这些结果只能回答「提供正确指导是否有用」，不能回答「检索能否选出正确的 Practice」——后者需要将检索接入对照之后才能检验。

## 如果重来一次

回顾整个过程，有四条规则如果在第一天确立，可以最大限度减少无效工作：

- **无关组应从第一个实验就存在。**它区分「增加一段文本有用」与「提供正确指导有用」，是全部归因的前提。
- **执行健康、语义硬门槛、质量信号必须分开记录。**混合记录的数据没有解读方法，这是登录页试运行暴露的问题。
- **judge 先通过判别力校准，再参与评分。**v1 的校准结果是方向相反的；v2 通过校准后投入使用，且始终仅报告参考分。
- **执行计划先登记后执行。**顺序、重复次数、补跑资格在执行前确定，失败与超时的运行保留在统计中。

目前的证据形态是：三个任务方向一致，oracle 组全部严格高于两个对照组；样本量很小，检索未接入对照，结论停留在方向性证据。我们不使用「证明」的表述，仅报告方向一致的信号。下一步是扩大样本、将检索接入对照，在正式协议下产出可以作为正式结论发布的结果——到那时，本文中的「不确定」才应被替换。
