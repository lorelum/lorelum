# Lorelum for omp

Source and maintenance notes for the omp Plugin. Installation and usage are documented in the [user guide](https://lorelum.com/en/docs/omp).

`.omp-plugin/marketplace.json` points to this package; keep its entry version and the package version in sync. `omp.extensions` loads `extensions/catalog.ts`, and `skills/lorelum/` packages the portable Skill and its references. Host imports are type-only; the Plugin has no runtime dependencies.

## Request behavior

- Session start/reload, switch, branch, tree navigation, and completed compact invalidate the snapshot. The next `context` callback reads once; subsequent requests reuse it. Concurrent callbacks share that read.
- Generation isolation and cancellation prevent an old read from reaching a new session. Shutdown cancels the outstanding read and closes the instance to late callbacks. The CLI read has a ten-second deadline and bounded stdout; stderr is drained without retaining a copy.
- Catalog metadata is prepended as a **user** text message in the `context` result. omp converts ordinary custom messages to developer priority, so the extension uses a user message to keep Pack descriptions below system policy. It does not persist the message or invoke query/get.
- Deduplication uses only identities generated by this extension; actual user or other extension messages survive, even if their text equals the Catalog. An unchanged message array is reused when possible.
- Any missing/old CLI, invalid response, nonzero exit, or timeout leaves no Catalog and does not retry at every request. There is one actionable diagnostic per loaded extension instance: UI warning in interactive mode, stderr otherwise. A new lifecycle boundary permits another read. A sub Catalog response of `{}` is normal when disabled, not a diagnostic. The Skill does not list Packs merely to compensate for a child's intentionally absent Catalog; independent task-required discovery remains available.
- Bash `tool_call` obtains a rewritten command from the CLI's `shell` bridge using the actual session ID. The CLI owns the shared lore-only/all-shell policy and quoting; the extension preserves other input fields and the native approval flow, without global environment changes.
- `before_subagent_spawn` captures the originating Main session at dispatch. All nested task/eval children inherit that origin through the module-local handoff, while native parent identity checks, collision rejection, and lifecycle cleanup remain in force. Factory-local event buses are not shared; this association does not replace Backend storage.
- Child requests lazily obtain bounded successful-get metadata from that Main through the unchanged CLI `read-hints` bridge and prepend a temporary user message. Each child's own gets are recorded under its own session, not automatically under Main. Missing or ambiguous origin identity never selects another session.
- `~/.lorelum/config.yaml` accepts boolean `agent.subagentPackCatalog`, default `false`. Main always receives the Catalog; children receive it additionally only when explicitly `true`. This adds Pack routing metadata, not full Pack or Practice bodies. Catalog requests accept optional `agentKind: "main" | "sub"` (omitted means Main); the extension marks child requests `sub`. The CLI alone reads the setting: disabled sub requests return `{}` without Store access, while enabled requests reuse the shared renderer even when no candidate origin is available. Candidate lookup is independent of this setting.
- The CLI reads the setting on the next sub Catalog bridge call. New children or the next session/compact refresh use the changed value; ordinary requests reuse the lifecycle snapshot. Reload can trigger refresh; Backend does not need restarting, and disabling Catalog never disables read hints.

## Verification

Run `bun test plugins/omp/lorelum` from the repository root. Tests use injected executors and subprocess streams; a real-host install and provider-payload check establish loading, Catalog delivery, successful get session association, and task/eval parent hints. The checkout workflow is in the [Plugin development guide](../../../docs/development/plugins.md#omp-checkout-install).

For type checking, use a temporary TypeScript configuration resolving the installed `@oh-my-pi` declarations. Do not add the host runtime as a dependency or commit a machine-specific path.

The Windows subprocess branch uses `cmd.exe` for `lore.cmd` and `taskkill /T /F` for cancellation. Platform acceptance evidence is recorded separately; implementation alone does not establish support.

The omp `context` callback has no task cancellation signal. The extension cancels its own read on deadline, lifecycle invalidation, or shutdown; it does not call `ctx.abort()` to stop the user's task.
