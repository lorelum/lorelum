# Lorelum Query 分阶段实施规划

- 状态：Proposed，供拆分后续 issue、设计决策和验收使用。
- 日期：2026-09-06。
- 状态复核：2026-09-06，get 已通过 PR #50 合入 main（`833444fdcf63f9cc9dbbb42395174132701d813b`）。
- 范围：关键词检索、配置、Embedding、派生索引、向量与混合检索，以及后续质量和性能演进。
- 本文不代表所列命令或字段已经实现，也不替代 Accepted ADR。示例命令、配置路径和状态名均为设计建议，需在对应阶段对齐后实现。

## 1. 目标与推进原则

让 Agent 先能够从已安装的 Practice 中找到相关规范，再逐步提升同义改写、跨语言和复杂适用条件的检索质量。`query` 返回候选摘要，`get` 按稳定 ID 读取完整原文，两者分别演进。

采用增量交付顺序：

**get（已合入 main）→ 可独立使用的关键词 query → 配置基础 → Embedding profile/provider → 可恢复的派生索引 → 向量与混合 query → 按评测增强。**

每阶段必须有独立价值、明确退出条件和有限改动范围。后续阶段的接口预留不能变成前一阶段的交付依赖；尤其不能为了关键词检索，先完成完整 config 系统、模型下载器和向量数据库。

规划遵循以下原则：

1. 内容来源继续是 LocalStore 的 Effective Practice，检索层不重新解析 Pack 或裁决同 ID 的内容冲突。
2. 关键词检索始终是无 Embedding 配置、无模型下载、无网络要求的基础能力。
3. 模型配置与索引绑定显式管理；不同向量空间不能混用，即使维度相同。
4. 内容安装、索引构建、查询可用性分别表达；一个成功不代表另两个已经完成。
5. 先建立真实任务基线，再增加模型和基础设施复杂度。
6. 本规划只包含通用设计与合成示例；私有 Pack、评测答案、真实查询和运行日志不进入公共仓库。

## 4. M0：按 ID 获取完整 Practice（已完成）

PR #50 已于 2026-09-06 合入 main，Issue #49 已关闭。已交付契约见[合并提交中的 get 文档](https://github.com/lorelum/lorelum/blob/833444fdcf63f9cc9dbbb42395174132701d813b/docs/cli/get.md)。该能力返回完整 canonical Practice、contentDigest 和来源，沿用 LocalStore 的验证与恢复行为，不提供跨命令快照或版本固定。

后续回归关注：精确读取、未找到、参数错误、来源合并、完整正文、Store 隔离、持久化后跨进程读取和既有恢复路径。这些不再作为待实现的 M0 工作；新增检索基础设施应保持 get 不依赖 Embedding 配置或语义索引 ready，LocalStore 自身不健康时仍遵循其契约。

## 5. M1：先交付关键词 query

### 范围与实现建议

先从 `LocalStore.open()` 的一致快照中构造词法检索输入，以 Practice 为返回单位。优先评估进程内 BM25；如果采用更简单的确定性加权 token-match，必须在设计中标明算法和局限，不将其称为语义检索，也不能声称它与 BM25 等价。

为避免前置存储工程，第一版可以在进程内构建词法索引，不要求引入 SQLite FTS 表。现有读取路径本来就会物化完整快照，先测真实 Pack 的冷启动成本，再决定何时持久化词法索引。若采用检索库，需要评估维护状况、Bun 兼容和许可证。

建议索引字段为 id、title、applies_when、stage、tech_stack、body 和反模式文本，单独保留字段权重。query 与文档使用一致、版本明确的 tokenizer，覆盖英文大小写、中文短词、CJK 连续文本、中英混排、点分 ID、camelCase 等技术表达。

### 阶段设计需要冻结

- 输入与 top-k 的范围、默认值及参数错误行为。
- 摘要字段、确定性平局排序和合法空结果；摘要与正文读取的边界。
- 字段权重、tokenizer 和零匹配判定。相似度高不代表适用条件成立。
- 是否返回计数；不要继承一个未来无法保持的“全库精确总命中数”。候选数、返回数和全库命中数必须分开命名。
- 排名分数默认作为内部信息；若公开，明确算法/版本与不可跨模式比较的限制。
- 是否从第一版返回实际检索模式、内容 digest 或快照标识。跨 query/get 的版本固定是单独设计点，不能因为返回 ID 就声称跨调用一致。
- CLI 的 registry/discovery、JSON envelope、typed error 和共享 Store-root resolver。

不要预先公开尚未实现的 semantic/hybrid 参数、structured filter 或索引控制命令。engine 可以保留窄的检索边界，后续适配器扩展不需要提前承诺完整用户接口。

### 退出条件

有命中、无命中、空 Store、空白输入、中英文与技术标识符均有回归覆盖；排名在同一快照和算法版本下确定。安装、升级、卸载后新调用读取当前内容，不引入第二套内容来源。

真实进程验证 query → get、显式 Store 隔离及单行 JSON；记录真实 Pack 的 CLI 冷启动耗时、峰值内存及词法 Recall/Precision 基线。只把这一阶段称为关键词检索已交付。

## 6. M2：配置基础与 config 管理

### 配置先解决哪些问题

区分四种概念：用户期望的检索模式、provider 连接与运行参数、不可变 Embedding profile、某个 Store 实际已就绪的索引。配置文件不是索引状态的事实来源。

建议第一版仅支持显式选中的 Store 配置，候选位置为 `<store-root>/config.json`，由配置模块独立拥有 schemaVersion。该路径需在本阶段对齐，不是当前 Store 既有文件。暂不自动发现仓库配置，不读取用户默认 Store 的配置作为另一 worktree 的隐式覆盖层。

解析 Store 根目录继续只走共享 resolver，不让配置里的路径反过来重定向 Store，避免循环解析。未来用户全局 provider 定义或项目配置确有需要时，再设计继承与信任边界。

建议普通运行参数的优先级为：已支持的显式 CLI 选项 → 明确列入白名单的环境变量 → 选中 Store 的配置 → 内置默认。没有正式定义的环境变量不参与解析，尤其不改变已有 Store-root 语义。解析结果携带各字段来源，并对合并后的整体重新验证。

### 配置内容与管理能力

| 配置类别 | 例子 | 行为 |
| --- | --- | --- |
| 检索偏好 | 模式、结果数量、期望 profile | 不改变既有索引的实际状态 |
| Provider 连接 | provider 类型、endpoint、credential 引用 | 明确本地/远程及数据发送目标 |
| 编码参数 | 模型标识、版本、维度、指令、归一化和截断策略 | 生成新的不可变 profile，不原地修改旧 profile |
| 运行参数 | timeout、batch size、有限重试 | 不改变向量空间时不触发重建 |
| 构建策略 | 显式构建、资源预算、失败处理 | 不把一次配置写入升级为隐式计费任务 |

候选命令形态是 `lore config show/get/set/unset/path`，此处只列能力，不冻结语法。首个 PR 可以只提供解析与只读诊断，写入能力单独交付。所有命令遵循现有 Agent-first JSON 协议与 discoverability。

API key 初期优先使用环境变量引用或凭证存储引用，不要求把密钥写入配置。show/get/诊断均不得展开凭证值；新增 endpoint 配置与本地服务暴露也不能无意成为日志内容。替换 key 本身不要求重新 Embedding。

配置读取不打开或修复内容 Store；没有配置时使用阶段定义的默认值。写入采用验证后的原子替换及并发保护。未知 key、错误类型、损坏文件和不支持的配置版本明确报错，不能默默启用另一个 provider。

### 退出条件

优先级、字段来源、默认值、无效配置、schema 迁移、并发写入、敏感值隐藏均经过验证。对隔离 Store 运行 config 不读写默认 Store，不更改内容 generation/effectiveRevision，不自动联网、下载模型或建立向量索引。配置缺失、路径解析失败和环境变量污染均有跨根测试，不能因为选中 Store 的配置不可用就回读默认 Store；已有显式 Store-root 解析规则保持不变。

## 7. M3：Embedding provider 与向量空间身份

### 先区分“连接配置”和“向量空间”

相同模型名不保证相同权重，相同维度更不保证兼容。需要持久化不可变的 EmbeddingProfile，由确定性序列化后的编码契约生成 profileId，而不是用用户起的别名或 `model + dimensions` 作为唯一身份。

| 身份内容 | 原因 |
| --- | --- |
| provider/部署命名空间、模型 ID、可固定的 revision 或权重标识 | 防止同名模型、不同部署产生不同空间 |
| 文档编码与 query 编码的配对契约 | query/passage 前缀或 instruction 可能不同，但必须来自同一已验证组合 |
| 实际输出维度、pooling、归一化和距离度量 | 维度正确不代表处理方式相同 |
| tokenizer/截断策略、文本投影版本 | 模型输入构造变化会改变可比较性或索引语义 |
| 会改变输出的量化/运行时版本 | 无明确兼容证据时，按新 profile 隔离 |

provider 不暴露不可变 revision 时，记录可取得的标识并承认不能自动证明权重未漂移；禁止将维度探测当作同一空间的证明。部署变更、服务方模型迁移或无法确认兼容时显式重建。

密钥、日志路径、重试次数通常不进入 profileId。endpoint 变更可能只是路由变化，也可能换了模型：默认保守隔离，只有明确的空间身份与兼容证据才允许复用。先分别比较两种模型在同一任务集上的表现，不直接比较它们的向量或原始 cosine 分数。

### Provider 实现路径

engine 定义窄接口：描述编码契约、文档批量编码、query 编码、结果验证与 typed error；配置解析与网络适配各自拥有边界。

先用 fake provider 验证批次乱序、返回数量不符、维度错误、NaN/Infinity、零范数、取消和超时。随后每个适配器单独交付，至少比较一个本地多语言候选与现有 ADR 的在线基线。协议兼容不意味着模型指令、鉴权和错误语义完全一致。

本地路线优先评估用户管理的本地服务，避免首轮同时承担下载、进程管理和二进制内嵌推理。它仍需要已安装的模型与活跃进程；远程路线需要明确的 endpoint、凭证和联网选择。默认本地还是远程在模型质量/运行成本评测后对齐，不在此预先改变 ADR 0002。

### 退出条件

每次编码都能说明所用 profile；凭证缺失、网络失败、模型不可用与非法向量明确失败。测试 mock 网络，真实模型验证在隔离 Store 中单独记录，不能把 fake 测试通过称为模型质量通过。

## 8. M4：派生索引与 LocalStore 的有限改造

### 存储所有权

保留 LocalStore 为内容与来源的事实来源，新增独立的检索存储模块。候选布局如下，具体路径需在存储 ADR 中冻结：

```text
<store-root>/
  ...existing LocalStore files...
  config.json                 # 配置模块拥有
  indexes/
    retrieval.sqlite          # 检索模块拥有，独立 schema 版本
```

优先评估独立 SQLite 文件，避免让 LocalStore 的 `PRAGMA user_version`、reindex 或恢复逻辑承担向量表所有权。拆库不提供跨库事务，因此内容快照与索引发布必须通过显式身份、revision、digest 和完整性校验协调。

| 派生实体        | 最小信息                                                              |
| --------------- | --------------------------------------------------------------------- |
| Profile         | 不可变编码契约及 profileId                                            |
| EmbeddingRecord | profileId、实际输入 digest、向量值和形状                              |
| Binding         | Practice ID、contentDigest、视图 ID、EmbeddingRecord 引用             |
| Snapshot        | Store 绑定、profileId、目标/就绪 revision、投影版本、完整性摘要和状态 |
| BuildJob        | 幂等键、目标、进度、重试信息及失败状态                                |

相同内容的向量可以在同一 profile 内复用，但跨 profile 一律不复用。第一版缓存限定在选中 Store 内；跨 Store 全局缓存留后续，以免引入隔离和删除语义问题。

`effectiveRevision` 只是单个 Store 内的计数，不能独立证明索引属于同一内容集。索引 manifest 应验证根目录绑定和当前 Effective Practice 集的 digest/数量/ID，避免复制错误索引或 Store 重建后计数碰巧相同而误用；若采用持久 Store UUID，需要单独对齐 LocalStore 契约和迁移。

### 生命周期与构建状态

```text
未构建 → 构建中 → 就绪
构建中 → 失败/取消 → 可恢复构建
就绪 → 内容或目标 profile 变化 → 待更新
```

这些是内部状态概念，CLI 错误和 JSON 字段在本阶段单独定义。一次构建固定目标 profile 和不可变内容快照；结果先写 staging，验证所有绑定后原子发布。LocalStore 持续更新时，可完成旧快照但不能标成当前就绪；调度新目标或保留明确过期状态。

Embedding 计算在 SQLite 内容写事务外。outbox 是至少一次通知，消费必须幂等且可重试。建议新增的异步索引消费者只有在构建请求持久化后才完成 hook 回调，不能将内存 promise 当成可恢复任务；CLI 退出时也不能丢失任务。这是 M4 要对齐的消费者语义，不代表 ADR 0007 已实现或承诺构建任务系统。

建立索引时还必须支持直接对账当前完整快照：过去未安装消费 hook、已被默认 no-op 确认的历史事件，不会因为新增索引器自动重新出现。delta 用于增量优化，不是恢复完整索引的唯一依据。

### 哪些变化需要什么动作

| 变化 | 必要处理 |
| --- | --- |
| Practice 新增/正文变化 | 为改变的输入生成或复用同 profile 向量，建立新绑定 |
| Practice 删除 | 从可发布绑定集中移除，不允许历史向量继续召回 |
| 只有来源增减 | 更新/读取当前来源；不能只按 effectiveRevision 缓存 provenance |
| LocalStore reindex | 与当前快照重新对账；内容和 profile 均相同可复用向量，不等于必须重新计费 |
| 切换模型/维度/编码契约 | 建立独立 profile 和新索引，禁止原地混写 |
| 仅替换凭证/timeout | 不改变空间时无需重建 |
| 词法 tokenizer/投影改变 | 重建对应词法派生状态；不要误触发所有模型重新编码 |
| 翻译检索投影改变 | 若纳入检索，单独按 locale/翻译 digest 失效，不能只依赖 canonical revision |

### 模型切换流程

配置选择 B → 记录期望 profile B → 显式构建 B → 校验 B 与当前内容 → 明确启用 B。A 的索引在此期间保持隔离，可供显式选择或回滚，但不能冒充 B 的结果；回滚 A 仍须校验其与当前 Store 的一致性。

配置里“想用 B”和索引里“B 已 ready”是两件事。原子启用时应校验配置版本或期望 profile，避免用户已改选 C 后，B 的构建完成又把 C 覆盖。旧 profile 的清理是独立操作，不在一次配置写入中自动删除。

### 跨文件发布与迁移协议

M4 存储 ADR 必须先冻结以下协议，不能把两个文件的各自原子写入误认为跨文件事务：

- config 记录期望目标，索引数据库中的 active snapshot 指针是“已启用”的唯一事实来源。启动对账时显式展示二者不一致，不回写配置来伪装切换完成。
- 建议 config 写入与快照启用共用短时协调锁；启用时在锁内重读配置并校验内容摘要/版本，再由索引数据库事务发布快照及 active 指针。昂贵编码不持有该锁，所有正式写入入口都遵循同一协议。
- 每次查询固定所选 profile 与内容快照；目标配置和 active 指针不匹配时，按 M5 的未就绪语义处理，不因保留了 A 就静默用 A 服务 B。
- 配置已指向 B、数据库发布前崩溃时，重启仍识别 B 未启用；数据库事务提交后崩溃时，以完整提交的 active 指针恢复，不能依赖内存“完成”标记。
- 索引 schema 迁移先检查版本并采用事务化升级或新文件构建后替换；具体选一种写入/恢复协议。中断时以最后完整提交且版本兼容的 DB 为准；无法确认兼容则语义索引不可用，关键词/get 继续依赖健康 LocalStore。

协调锁不是内容 Store 的事务锁，也不自动冻结正在变化的 Practice；内容变更仍通过目标快照和发布/查询校验处理。绕过 CLI 手工编辑配置的并发写入不承诺事务隔离，但每次查询必须验证实际 profile 兼容，不能把向量混入另一空间。

### 控制能力与退出条件

需要提供查看索引状态、显式构建/重建、失败恢复及过期索引清理能力。候选命令族可为 `lore index ...`，但名称未冻结；必须与恢复内容 Store 的 reindex 区分，不能复用同一个名字而隐藏两种破坏范围。

测试覆盖重复事件、断电/进程退出、并发构建、更新期间查询、迁移失败、缺失/损坏索引、复制错误索引、旧 Store 初次接入和模型切换。存储 schema 升级不得覆盖未知的新版本；不兼容的派生文件可以隔离后重建，但不删除内容事实来源。

## 9. M5：向量与混合 query

在已就绪的单一 profile 上实现精确 cosine/等价点积召回；先用 SQLite 持久化 Float32 向量并在内存扫描，暂不引入 ANN。向量空间身份校验先于打分，query 编码必须与该索引 profile 配对。

关键词与向量各自召回候选后，用 RRF 等按名次融合的方法合并到 Practice。不直接相加 BM25 与 cosine 原始分数，不把某个固定相似度当成通用适用概率。第一版先评测单向量投影，再决定是否需要多视图或分块。

候选模式为 keyword、semantic、hybrid，参数拼写待 CLI 设计对齐。建议显式 opt-in 语义能力，安装模型或更新配置文件不能未经约定改变默认关键词行为。

| 请求与状态                                    | 建议行为                                       |
| --------------------------------------------- | ---------------------------------------------- |
| keyword，无模型/向量索引                      | 正常运行，不依赖 Embedding provider            |
| semantic/hybrid，目标索引完整且 provider 可用 | 使用同一 profile 和一致快照查询                |
| semantic/hybrid，索引未建/过期/损坏           | 明确报错并提供恢复方向                         |
| semantic/hybrid，provider 不可用              | 明确报错，不自动改用其他模型或云服务           |
| 显式允许 keyword 降级                         | 返回实际执行模式及原因，不能伪装成 hybrid 成功 |
| 无相关候选                                    | 合法空结果，依据经评测的策略，不强行填满 top-k |

如果后续允许自动降级，需要在对应设计中冻结机器可读状态和质量含义。索引故障不应导致关键词模式读取陈旧内容：降级读取当前 LocalStore 快照。

离线语义查询要求本地 query encoder 可用；只有远程模型生成的文档向量并不足够。跨调用 query/get 一致性应通过 digest/快照设计明确，不能用索引内部 revision 暗示现有 get 已支持版本固定。

退出条件：同一评测集对比 keyword、dense、hybrid；验证关键词模式无网络、模式错误与空结果、模型隔离、当前内容和来源一致性。分别记录 CLI 冷启动与长驻服务热路径成本，不以向量循环耗时替代端到端延迟。

## 10. M6：由证据决定增强方向

| 观察到的问题                  | 优先检查                     | 有证据后再引入             |
| ----------------------------- | ---------------------------- | -------------------------- |
| 同义表达/跨语言漏召回         | 模型、输入前缀、投影、截断   | 更合适的多语言模型、多视图 |
| 相关候选已召回但排位差        | 字段权重、融合、否定/例外    | Cross-encoder reranker     |
| 无关规范造成任务越界          | 适用性标注、过滤、空结果策略 | 更严格精排和预算选择       |
| CLI 慢而向量扫描快            | Store 验证、加载、模型冷启动 | 模型复用、缓存或常驻运行时 |
| 向量规模确实超出内存/延迟预算 | 实际向量数、维度、扫描成本   | ANN、嵌入式向量库          |
| 多用户共享/高并发             | 部署与一致性边界             | 共享数据库和独立检索服务   |

MCP adapter 可以在关键词 service 稳定后另行推进，无需等待所有 M6 优化；但必须设计长驻进程的 Store/config/profile 刷新和请求快照隔离，不照搬 CLI 每次冷开的生命周期。

LLM query rewrite、GraphRAG、自动研究、微调和内嵌模型下载器均不作为早期前置条件。

## 11. 评测与工程验收

从 M1 开始保留统一质量基线，后续模型共用独立的测试集。可从 100–200 个经人工确认的任务起步，按任务族或 Pack 留出，避免同模板改写同时进入调参集和验收集。

标注应包含必须召回、辅助相关、不适用/越界，而不只包含一个正例。覆盖中文、英文、中英混排、同义改写、技术名、否定条件、相似但不适用、无答案、未知 Pack 和长文本。

| 维度       | 验证内容                                                             |
| ---------- | -------------------------------------------------------------------- |
| 召回       | Recall@k，按语言和任务类型分组                                       |
| 排名       | Precision@5、nDCG@5、不可用结果占比                                  |
| 适用性     | 越界误报、无答案误报，不把相关性当成授权                             |
| 运行成本   | CLI 冷启动/MCP 热路径 p50/p95、峰值内存、模型下载、首次/增量构建成本 |
| 存储正确性 | 内容更新、删除、恢复、并发、配置切换和 profile 兼容验证              |
| Agent 效果 | 实际遵循规范与任务范围，独立于检索引用次数                           |

具体数值门槛在获得基线后由阶段验收冻结。公开 CI 使用合成 fixture 和 mock provider；真实模型结果、私有数据集和云调用记录在独立评测环境保留。单测通过、模型能够运行和检索质量达标分别报告。

实现 PR 按改动范围完成 `bun test`、typecheck、lint、格式及相关真实进程 integration；检索和存储新增行为有对应测试。本文仅为文档，不代表这些实现验收已经执行。
