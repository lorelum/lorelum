# 真实任务评测集建设计划

> 日期:2026-10-08。读者:Lorelum 维护者与检索实验实现者。状态:**计划草案,未执行**。它回答"现在的真实命中率是多少、改动是否真有效",不改变生产公式、公共 schema、CLI/API,也不授权进入方案 C 的 G2/G3。证据来源:[verification §26](../../openspec/changes/advance-task-aware-semantic-retrieval/verification.md)。

## 1. 为什么要做

| 事实(§26) | 含义 |
| --- | --- |
| 旧 50 例 hit@5 45/50 | 反复用于调试,偏乐观,不能代表真实水平 |
| pilot D(40 条真实提示):10 条有目标,control 成功 5/10 | 样本太小,5/10 的 95% 区间约 19%–81% |
| pilot D 中 30/40 无任何可接受目标 | 语料覆盖与排序两类问题混在一起,现有数字分不开 |
| 角色(Q、Q+I)与概括视图(S)均无收益 | 在 10 条有目标 query 上分辨率不足,不是"已证无效" |
| 标注为单评审 agent,`labelsIndependent=false` | 任何"通过"都不可能成立 |

结论:继续在现有数据上改表示或公式只会在小集合上过拟合。需要先让**度量可信**。

## 2. 要回答的问题与不回答的问题

回答:

1. **覆盖率**:真实任务中有多大比例,语料里确实有可接受的 Practice?
2. **排序质量**:在有目标的任务里,control 把它们排进前 K 的比例,及禁项出现率?
3. **变化是否有效**:某个改动相对 control 的逐例改善与回归,是否超出噪声?

不回答:不选新模型、不设计新表示、不讨论产品接入。这些等度量可信后再谈。

## 3. 度量(预先固定)

| 指标 | 定义 | 分母 |
| --- | --- | --- |
| 覆盖率 | 至少有一个 required-core 或 sufficient-alternative 的 query 比例 | 全部 query |
| 成功率 | 前 5 名 fullyServed 且无禁项 | 有目标 query |
| any-help | 前 5 名含至少一个可接受 Practice | 有目标 query |
| 禁项率 | 前 5 名含 forbidden | 全部 query,并单列有目标子集 |
| 未判定率 | 前 5 名中 undetermined 或 unlabelled 槽位占比 | 前 5 槽位 |
| 逐例改善/回归 | 与 control 的配对差异 | 有目标 query |

覆盖率与成功率**分开报告,不合并成一个综合分**。分母不同,不得互相冲抵。置信区间用 Wilson;配对比较用精确 McNemar 或符号检验,同时给出不一致对数。

## 4. 样本规模

按 pilot D 的覆盖率约 25% 估算:

| 目标 | 需要有目标 query | 需要总 query |
| --- | --- | --- |
| 成功率区间半宽 ≤ ±15pp | 约 43 | 约 170 |
| 成功率区间半宽 ≤ ±10pp | 约 96 | 约 380 |
| 检出 control 与候选各 50%、70% 的配对差异(不一致对中 80% 偏向候选,α=0.05) | 约 40–60 | 约 160–240 |

这是工作量估算,不是功效保证;覆盖率若低于 25%,总量需相应放大。同源改写按任务簇计,不当独立样本。

## 5. 来源与采集

1. **来源**(按优先级):
   - 维护者与协作者给 coding agent 的真实请求(需授权与范围声明)。
   - 已授权的公开讨论中的"怎么做事"类问题(不是产品缺陷报告;§26.11 已证明产品 issue 标题几乎无目标)。
2. **固定规则采集**:先写规则(形式过滤、每会话或每作者上限、时间范围、种子),再抽样;**不按 Practice 内容挑 query**。
3. **分层与留出**:
   - 按**项目/来源**、**时间**、**语言**记录;不预先按目标覆盖挑选。
   - 采集时就划分 **dev**(可用于诊断)与 **holdout**(冻结前不得查看排名、不得用于选改动)。holdout 至少 40% 且来源独立。
4. **隐私**:原文、标签、向量与运行产物放仓库外;仓库只保留规则、计数、摘要。不提交会话原文。
5. **覆盖分层**:允许事后补采"薄弱/多意图/无目标"各 ≥ 10 条,但补采规则同样先写后抽,不用作调参依据。

### 5.1 协作者交付规格(由协作者自行导出,我不读取其原始会话)

- **导出范围**:一个明确的时间区间内,**该协作者本人输入给 coding agent 的全部用户消息**,不要自己挑"好用的"。抽样由评测方按固定种子规则做,否则会引入选择偏差。
- **不要包含**:助手回复、工具输出、系统/注入的上下文、文件内容、子 agent 的任务提示。
- **格式**:UTF-8 JSONL,每行 `{"id": "<随机或哈希,不含个人信息>", "contributor": "<匿名代号,如 c01>", "session": "<匿名会话代号>", "ts": "<年月即可>", "project": "<粗粒度类别,如 web / backend / docs / research,可省略>", "text": "<原文>"}`。
- **脱敏(导出方先做,规则一致)**:密钥、令牌、邮箱、手机号、绝对路径里的用户名、内部仓库或客户名。脱敏处用固定占位符(`<SECRET>`、`<EMAIL>`、`<PATH>`、`<ORG>`),不要删句子。
- **同意声明**:每位协作者附一份简短声明:用途(检索评测)、保留期限、可要求删除。
- **不做**:不在导出时去重或筛长度,这些由评测方的固定规则完成。

## 6. 标注:agent 面板初标 + 人工审理由

人工不从零标注,而是**审 agent 给出的对比理由**,并且只审抽样出来的、对结论影响最大的那部分。

### 6.1 agent 面板

- 每条 query 由三名互不可见的评审标注,至少两个模型家族(家族不够时披露)。多数票定类别;不一致交第四名裁决,裁决必须写理由。
- 评审必须读 query 和 Practice 全文;每个非 irrelevant 标签附一句 Practice 原文引用,脚本用字符串匹配核对。引用对不上的标签作废重标。
- 评审看池化候选(多个系统前 10 名 ∪ 评审初选),打乱顺序、隐藏来源;不看排名与条件。

### 6.2 理由卡(人工审阅的对象)

每条被抽中的 query 生成一张卡,只含:

1. query 原文(不含来源、不含系统排名)。
2. 面板结论:选中的 Practice 及类别(required-core / sufficient-alternative / forbidden / 声明无目标)。
3. **为什么选它**:引用 Practice 的 `When to apply`/`Exceptions` 中支持适用的原文,以及 query 里对应的条件。
4. **为什么不选邻近的那条**:最相近的 1 到 2 个落选 Practice,引用其排除条件(`Exceptions and boundaries`、反模式、适用阶段不同)说明为什么不适用。
5. 面板内部分歧(如有)与裁决理由。

人工对每张卡只做:**接受 / 拒绝 / 无法判断**,拒绝须写一句话原因。约 30 到 60 秒一张。

### 6.3 抽样(优先审"影响结论"的)

| 层 | 内容 | 抽样 |
| --- | --- | --- |
| A | 面板有分歧、需裁决的 query | 全部审或至少 50% |
| B | 判 required-core / sufficient-alternative 的 query(决定分母与命中) | 随机 30% |
| C | 判 forbidden 的 query(决定禁项率) | 全部审 |
| D | 声明"无目标"的 query(决定覆盖率) | 随机 20%,另加"系统前 3 名里有面板标为 irrelevant 的"全部审 |
| E | 金丝雀:故意改错类别或把近邻 Practice 换进"为什么选它",混入已知错误的卡 | 约 10% |

预计 100 到 150 张卡,约 1 到 2 小时。

### 6.4 防止人工只是点头

- 理由写得通顺会让人倾向接受。金丝雀卡测人工是否能发现错误:金丝雀检出率低于 80%,本轮人工抽查不计为有效校准,须重审。
- 卡不显示面板的置信度或多数票比例,避免锚定。
- 人工看不到任何系统的排名,也不知道哪条是金丝雀。

### 6.5 结果如何进入度量

- 按层估计面板错误率及 95% 区间(Wilson)。拒绝的卡按人工结论改标,并据此重算成功率、覆盖率。
- 某层拒绝率超过 15%,该层整体重标(换评审或收紧协议),不是只改被抽中的那几张。
- 报告面板与人工一致率(Cohen's κ);**κ ≥ 0.6 且金丝雀检出率 ≥ 80% 才允许在 §9 报"通过"**。否则结果标"参考性"。
- 抽查结论按层汇报,不合并成一个一致率。

### 6.6 仍然成立的限制

- 面板的共同盲点(对"什么叫服务了这个任务"的共同误解),理由卡能让人看到推理,但人只审抽样,没抽到的错误不会被发现;区间会反映这一点。
- 任务提供者最清楚任务需要什么,若有机会让协作者审自己那批 query 的理由卡,效果优于第三方。
- 已有教训:评审曾只读 `applies_when` 或 query 被截断,引用核对就是为此加的。

## 7. 评测运行

- 复用 G0 的隔离重放与评分,不改生产 `scoreSemanticPractice`、golden pin、Profile、schema。
- 每个条件对全部 eligible Practice 评分,K 最后应用;保存完整排名与 manifest 后才读标签。
- 新数据只增加 query 与标签,不改 Pack 内容、模型与文档视图。
- 冻结后的 holdout 只在**一次**最终比较中使用;之后若再改动,须换新留出集。

## 8. 阶段与退出条件

| 阶段 | 产出 | 退出条件 |
| --- | --- | --- |
| E0 规则与协议 | 采集规则、分层、标注协议、指标与样本量的一页文档,版本化 | 维护者确认来源与授权范围 |
| E1 试采与试标 | 20 条小批,检查格式、标注耗时与一致性 | 格式可用,标注者一致性可接受;否则修协议 |
| E2 正式采集 | ≥ 170 条(目标 ≥ 380),dev/holdout 已划分 | 覆盖率与目标数达标,或明确"证据不足" |
| E3 标注 | 双评审标签与分歧报告 | κ、未判定率、程序性缺陷已披露 |
| E4 基线 | control 的覆盖率、成功率、any-help、禁项率与区间,分层子集(Pack、语言、来源) | 区间半宽达到 §4 目标,或记为不确定 |
| E5 分诊 | 失败归类:语料无目标 / 排序错 / 标注分歧 / query 过短 | 仅用于决定下一步方向,不调参 |

每阶段只进入下一阶段,不自动推进 G2/G3。

## 9. 失败与停止规则

- 覆盖率 < 10%:先补语料或缩小适用范围声明,而不是继续调排序。
- **可用线(维护者 2026-10-08 确定)**:有目标 query 上的成功率(前 5 fullyServed 且无禁项)约 80%–85% 以上算通过。操作化如下,在看到任何新数据前固定:
  - **通过**:全部有目标 query 合并后,成功率点估计 ≥ 85%,Wilson 下界 ≥ 80%,且禁项率不高于现有 control 水平。以 95 条有目标计,约需 ≥ 88% 命中才能满足下界。
  - **边缘**:点估计在 80%–85% 之间,或点估计 ≥ 85% 但下界 < 80%:记"不确定",补样本,不放宽。
  - **未通过**:点估计 < 80%。
  - 判定在**合并集**上做。holdout 约 38 条有目标,单独只能给出 ±14pp 的区间,不足以证明 80%-85% 线,因此 holdout 只用于检验改动是否过拟合,不单独做通过判定。
  - 同时报告 any-help;可用线只针对成功率。若成功率 < 80% 而 any-help ≥ 85%,说明问题在"完整服务"而非找不到,按 §8 E5 分诊。
- 成功率通过后:停止检索改动,转做覆盖与维护。
- 区间过宽:记"不确定",补样本,不放宽判定。
- 任何改动要采用,须在 holdout 上相对 control 有统计上不依赖单例的改善,且禁项不增加、未判定率可比。

## 10. 需要维护者决定

1. ~~可用线~~ 已定,见 §9。
2. **来源与授权**:是否继续使用你的 Codex 会话;是否有协作者或其他项目的真实请求可以纳入;范围与保留期限。
3. **评审**:有无至少一名人工评审可参与相关性标注及投入量。
4. **预算**:总 query 量**已定为 380**(约 95 条有目标,按覆盖率 25% 估;覆盖率更低则需相应追加);时间待定。
5. **覆盖口径**:语料没有目标的任务,是否属于需要补 Pack 的缺口,还是明确"不在适用范围"。

## 11. 不做的事

- 不在现有 50 例或 pilot A–D 上继续选改动。
- 不为凑数改写任务、不按 Practice 反向编写 query。
- 不以综合分掩盖覆盖与排序差异。
- 不因计划存在而修改生产检索、Profile 或公开 schema。
