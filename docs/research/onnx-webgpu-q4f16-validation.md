# WebGPU Q4F16 最小验证

结论：社区 Q4F16 原文件在本机运行时无法加载。修复 Cast 目标类型后的本地实验副本可以运行，512-token 编码比同轮 FP32 WebGPU 快约四成，进程 RSS 较低；同一小型合成检索集未见指标下降。修复副本不是可直接交付的社区原件，也不代表量化无损或 GPU 性能上限。

本次仅验证用户指定的 Q4F16，未改产品代码、生产依赖、config 或 Store，未提交、推送。[结构化证据](./onnx-validation/q4f16-results.json)保留资源摘要、修复清单、性能和检索结果；复用[前次冻结样本](./onnx-validation/quantization-fixture.json)。模型、探针、原始日志均留在忽略目录。

## 原文件失败与实验修复

固定社区仓库 `onnx-community/granite-embedding-97m-multilingual-r2-ONNX`，revision `536a9f241cb3f02a9c5995a1e708c784bd274859`。`onnx/model_q4f16.onnx` 为 154,468,150 bytes，SHA-256 `8a8d6fbeca35d4f363fdfd29413169e6690309614820225017853a825c63d7d9`，与 Hub LFS 摘要一致。

社区 tokenizer JSON 解析后与官方完全相同，配置差异仅为 dtype 声明和 Transformers 导出版本。性能基线为此前固定的官方 FP32 ONNX；本次未下载社区 FP32 权重作转换前后的逐权重对照。因此结果包含社区导出、量化和本地修复的共同影响，不能将差异全部归因于位宽。

原文件的 `/layers.0/attn/rotary_emb/Cast_1` 目标是 FLOAT，但 output value_info 声明 FLOAT16，ONNX Runtime 在 session 加载时拒绝；ONNX 1.19.0 的完整 checker 也报告 Cast 类型冲突。这发生在推理之前，原文件没有速度或检索成绩。

本地单独保存 `_castfix` 副本，将 35 个声明输出为 FLOAT16、但目标仍为 FLOAT 的 Cast 改为 FLOAT16。未改变权重；这是修改执行图，不能称为仅改元数据。副本通过 ONNX 完整 checker，但类型自洽不证明原标注正确或修复语义正确；SHA-256 `7c51fe06af64d11a0f3108f321e4a195617cf6d1c026045e16e11322f6c7e38c`。修复会降低这些位置的计算精度，尤其长上下文仍需专门验证；本次不是认可这一修复为最终导出方案。

## 执行路径和性能

硬件为 Apple M4 / 32 GiB / macOS 15.7.1 arm64。Bun 1.3.8、onnxruntime-node 1.29.0、tokenizers 0.2.0，WebGPU 优先并允许 CPU fallback，intra-op threads 4、inter-op 1。最终输出为 FP32 hidden state，仍在 CPU 做 CLS pooling 与 L2，未引入新的 GPU 后处理优化。

profile 显示 `MatMulNBits`、`MatMul`、`LayerNormalization`、`Softmax` 在 WebGPU 上执行，部分 shape/控制计算在 CPU。不是纯 CPU 回退，也不是全 GPU；trace 的事件时长不作为 GPU 核函数耗时或算力占用率。

独立进程按 FP32、Q4F16 副本、Q4F16 副本、FP32 顺序测两轮。沿用先预热 3 次、短查询 60 次、64-token 查询 40 次、文档 20 次、batch 10 次的端到端编码计时，包含 tokenization 和后处理，不含加载。

| 两轮测量范围         | FP32 WebGPU       | Q4F16 修复副本 WebGPU |
| -------------------- | ----------------- | --------------------- |
| 英文短查询 p95       | 6.45–8.89 ms      | 5.05–5.86 ms          |
| 中文短查询 p95       | 6.50–7.44 ms      | 4.58–4.62 ms          |
| 64-token 查询 p95    | 8.40–9.23 ms      | 6.39–7.00 ms          |
| 512-token 单文档 p95 | 46.72–47.69 ms    | 33.52–33.56 ms        |
| 512-token 单文档吞吐 | 21.39–21.53 条/秒 | 29.88–29.97 条/秒     |
| batch 8 × 512 p95    | 381.95–383.17 ms  | 252.99–260.84 ms      |
| batch 8 × 512 吞吐   | 21.77 条/秒       | 31.78–31.95 条/秒     |
| 完整负载后进程 RSS   | 1793–1806 MiB     | 1028–1037 MiB         |

单文档吞吐提升约 39%–40%，batch 8 提升约 46%–47%。RSS 约低 43%，但它不是 GPU 总内存/统一内存用量，也不包括所有瞬时峰值。固定 token 长度仍使用重复 hello，只是计算负载，不是真实文档吞吐承诺。

另外顺序测两种模型的 batch 1/8/32，每项预热 2 次后至少连续计时 10 秒；输入预分词，但包含张量组装、推理、完整输出回传和 CLS/L2。Q4F16 副本分别约 30.0、31.5、31.3 条/秒，同轮 FP32 分别约 21.4、22.2、20.8 条/秒；扩大 batch 没有明显继续增加吞吐。没有新增功耗、频率或计算单元占用率测量，不能称为吃满 GPU。

## 数值和检索效果

原有 8 组、10 个向量的 tokenizer ids/mask 完全一致；与官方 Python FP32 参考的向量余弦相似度为 0.9730–0.9911。输出有限但未达到原 FP32 parity 容差。最长仅 1025 tokens，不涵盖模型宣称的完整上下文。

复用 40 篇通用工程文档、30 个查询；文档和查询都由同一种模型独立编码，精确余弦排序，标签未修改。质量基线为前次保存的官方 CPU FP32 向量，其数值正确性已有参考对照；本次速度基线另为 WebGPU FP32。

| 检索指标   | 官方 FP32 | Q4F16 修复副本 |
| ---------- | --------- | -------------- |
| 第一名命中 | 25/30     | 25/30          |
| Recall@5   | 100%      | 100%           |
| MRR@10     | 0.9111    | 0.9111         |
| nDCG@5     | 0.9341    | 0.9341         |

70 个文本的向量余弦相似度均值 0.9903、最低 0.9832；1200 个 query-document 分数的绝对变化均值 0.0066、最大 0.0296。第一名 29/30 相同，唯一变化是两个均被标注相关的文档交换第一名，所有查询的上述指标保持一致；前五名集合平均重合 89.3%。

这只证明冻结的小型合成集合没有测出指标损失。不能称为无损，也不能推出 Q4 普遍优于 INT8：量化方案、保留精度和导出路径不同。本次没有真实用户查询、大规模近似候选、无答案阈值、混用旧 index 或长上下文质量验收。

当前判断：Q4F16 WebGPU 路径值得继续评估，但原发布件存在兼容性问题；修复副本的成绩不能转化成直接接入决定。正式采用前应有可靠的导出来源、修复数值验证，以及现有接入计划要求的隔离和分发验收。
