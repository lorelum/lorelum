# llama.cpp CPU：Q8 与 Q4 最小验证

选型已收口：用户确认采用 **llama.cpp + Q4_0 CPU**，停止本轮框架与量化调研，GPU 留待后续。以下保留当时的比较结果和建议；实施以[第二阶段接入计划](../plans/local-backend-stage-2-design.md)为准。

2026-09-11。结论：本机 llama.cpp 的 Q8_0 和显式全四位 Q4_0 值得作为 CPU 接入候选。单条 512-token 编码较本轮 ONNX INT8 有温和提升，512-token 配置下进程 RSS 更低；默认 Q4_K_M 反而更慢，且文件没有明显缩小。本阶段已选定 llama.cpp Q4_0；Q8_0 保留为量化质量对照，不同时交付两套 runtime。

本次只完成获准的验证和选型依据更新，未改产品代码、生产依赖、用户 config 或 Store，未提交、推送。[结构化结果](./onnx-validation/llama-cpu-results.json)保留两轮性能、量化摘要、数值和检索结果。所有模型、二进制、脚本及原始日志位于忽略目录 `.tmp-onnx-validation/`。

## 固定版本与正确性起点

- Apple M4 / 32 GiB / macOS 15.7.1 arm64。
- 官方 macOS arm64 llama.cpp release `b10901`，commit `28ff0958291ce3465fabd7bd679d4b0edd742bd9`；归档 SHA-256 `ba64da4bb1ba01dce65cd05d36e90d2cb22c7a2fb7cbc90e4911628138a1c34b`，已与 GitHub release 摘要核对。
- F16 GGUF 来自 ATF 转换，revision `cb3a901538f0b154ff9df54186fef4b3f52f0600`，206,403,072 bytes，SHA-256 `74075aeea7bd9ac4e5d74755e216fa487f5b6cce9ac6c5a363936370585b1a38`，与 Hub LFS 一致。
- Q8_0、Q4_K_M、Q4_0 都从同一个 F16 文件用上述 release 的 llama-quantize 本地生成，没有对量化文件再次量化。资源摘要和量化参数在结构化结果中。

先用 F16 对照官方 PyTorch FP32 参考：8 组输入、10 个向量，包括中英文、代码、Unicode、空白/空输入、混合长度以及最长 1025 tokens。移除参考 padding 后，token ids 全部一致；最低余弦相似度 0.9999999142，最大分量误差 7.10e-5，达到原先 FP32 参考校验的容差。这里证明本次版本和输入范围的模型支持，不代表完整上下文或所有语言已验收。

## 量化为什么未必缩小文件

| 产物 | 文件大小，十进制 MB | 实际情况 |
| --- | --- | --- |
| 官方 ONNX INT8 | 98.25 | 另需约 25.3 MB tokenizer 文件 |
| llama.cpp Q8_0 | 115.06 | GGUF 内含 tokenizer |
| llama.cpp Q4_K_M | 105.47 | 384 列不能满足部分 K 类型的 256 分块要求，量化器回退到 Q5_0/Q8_0；词嵌入表为 Q8_0 |
| llama.cpp Q4_0 | 66.35 | 使用 `--pure --token-embedding-type q4_0`，矩阵和词嵌入表均按 Q4_0 量化；norm 向量仍保留 F32 |

Q4_K_M 的回退和词嵌入表类型来自本次量化日志，不是根据文件名猜测。对这个模型，想明显缩小文件，选择能够覆盖 384 维词嵌入表的量化方式比单纯把名称改成 Q4/Q3 更关键。

## 同一 HTTP 入口的端到端 CPU 比较

驱动端相同，使用持久 HTTP 连接请求 `/v1/embeddings` 并解析、校验 384 维返回值。ONNX 实验端是 Bun.serve + onnxruntime-node 1.29.0 + tokenizers 0.2.0；llama 端是原生 llama-server。因此包含各自 HTTP、tokenization、推理和返回开销，是候选接入路径的比较，不是只比较底层算子。

两边均设 4 个推理线程。llama 使用 `--device none --no-op-offload -ngl 0`，实际日志确认 offloaded 0/13，模型和 compute buffer 均为 CPU；加载带 Metal 支持的原生库不代表执行 GPU。ONNX execution provider 只设 CPU。

正式性能比较按本阶段拟定的单条 512-token 上限配置，llama context/batch/ubatch 都为 512、parallel=1。每个独立性能进程只运行至 512 tokens 的负载，避免先跑长上下文正确性样例改变缓存和内存状态。两轮顺序为 Q8、Q4_K_M、Q4_0、ONNX，然后反向。每项预热 3 次，短查询采样 60 次、64-token 40 次、单文档 20 次、八条请求 10 次。

| 两轮范围 | ONNX INT8 | llama Q8_0 | llama Q4_K_M | llama Q4_0 |
| --- | --- | --- | --- | --- |
| 英文短查询 p95 | 2.63–2.72 ms | 1.53–1.78 ms | 4.23–4.31 ms | 1.44–1.48 ms |
| 中文短查询 p95 | 3.22–3.28 ms | 1.90–2.07 ms | 5.10–5.38 ms | 1.64–1.90 ms |
| 512-token 单条 p95 | 53.78–55.72 ms | 48.87–51.02 ms | 59.41–61.67 ms | 48.23–48.38 ms |
| 512-token 单条吞吐 | 18.36–18.93 条/秒 | 19.84–21.14 条/秒 | 16.52–17.18 条/秒 | 20.96–21.04 条/秒 |
| 刚 ready 的 RSS | 620–637 MiB | 316–321 MiB | 267–284 MiB | 260–261 MiB |
| 完整负载后 RSS | 870–888 MiB | 681–689 MiB | 649–666 MiB | 626–627 MiB |
| 进程启动至 ready | 418–525 ms | 633 ms | 525–623 ms | 625–628 ms |

Q8 单条吞吐按同轮配对提升约 5%–15%；Q4_0 约 11%–15%。Q8 工作负载后 RSS 低约 22%，Q4_0 低约 28%–30%。不能称为数倍提速或内存只需 300 MB。文件刚被下载和读取过，这不是冷文件缓存下的加载测试。

RSS 由 ps 每 200 ms 采样，不是完整瞬时峰值或孤立模型分配；共享桌面负载也会带来波动。早期 context/batch/ubatch=4096 的 Q8 进程在较长正确性测试后 RSS 超过 1 GiB。内存结论严格依赖输入上限和配置，不能把 512-token 数字外推到长上下文。

结构化数据保留八条输入请求的耗时，但不以此宣称底层 batch 优势：llama 单 slot 实际逐条编码八个序列，ONNX 一次执行 `[8,512]`。同一业务请求可以比较总耗时，但不能把内部执行策略当作相同。

固定长度负载使用重复 hello；它不是实际语料吞吐。重复输入缓存也经过代码和日志检查：此版本 CLS embedding 的不可拆分路径不进入 prompt-prefix 复用分支，每次日志均处理完整 token。仍不外推到其他 pooling 或生成模型路径。

## 检索与数值变化

沿用[冻结样本](./onnx-validation/quantization-fixture.json)：40 篇工程文档、30 个查询、10 个中文查询检索英文文档。文档与查询使用同一种精度，精确余弦排序；FP32 基线为已通过官方参考校验的 ONNX CPU 向量。本轮 ONNX HTTP 输出与前次 CPU INT8 检索结果一致。

| 指标                 | FP32 基线 | ONNX INT8 | llama Q8_0 | llama Q4_K_M | llama Q4_0 |
| -------------------- | --------- | --------- | ---------- | ------------ | ---------- |
| 第一名命中           | 25/30     | 26/30     | 25/30      | 25/30        | 25/30      |
| Recall@5             | 100%      | 100%      | 100%       | 100%         | 100%       |
| nDCG@5               | 0.9341    | 0.9464    | 0.9341     | 0.9318       | 0.9318     |
| 与 FP32 向量余弦均值 | 1         | 0.97379   | 0.99985    | 0.99666      | 0.98776    |
| 前五名集合平均重合   | 100%      | 84.0%     | 98.7%      | 93.3%        | 85.3%      |

Q8 的第一名与 FP32 30/30 相同，所有上述标签指标相同。两种 Q4 都在一个优雅停机查询中把相关文档从第三名降至第四名，导致 nDCG 小幅下降；Q4_0 另有一个第一名在两个均相关的结果间交换。不能用一题差异认定框架质量排名，也不能将余弦差直接换算成准确率损失。

Q8 数值最接近 FP32，但仍是有损量化：它在原有 10 向量参考测试中的最低余弦为 0.999687，不能写成通过原 FP32 的全部严格容差。真实用户查询、大规模近似候选、长上下文与无答案阈值仍未验收；此次小型检索抽样不替代后续质量评测。

## 接入与分发证据

整个官方 macOS arm64 release 解压后约 27.86 MB，包含 server、量化工具和配套 dylib。GGUF 自带 tokenizer，运行不需要 Python、Node 或额外 JS tokenizer。将完整运行目录复制到新位置，从 `/tmp`、仅 `/usr/bin:/bin` 的 PATH 启动 Q8 服务，全部 token/向量样例复测完成并正常退出。Python 只作为实验驱动端，不在被测原生服务内。

按当前实验资源直接相加，整个 release + Q8 GGUF 约 143 MB，+ Q4_0 约 94 MB；现有 ONNX 专用编译探针 + native 资源 + INT8 模型 + tokenizer 约 228 MB。它们不含共同的产品控制服务，也不是最终安装包/下载压缩体积，正式打包可能裁剪或复用资源。

llama.cpp 的接入收益是已有原生程序集中处理模型、tokenizer、pooling 和 normalization，减少 Bun Node binding/动态库加载适配；它没有消除原生库分发、私有 HTTP 端点、进程退出、超时和父进程异常回收问题。本次只验证正常启动、迁移目录、请求与终止，未做卡死、父进程死亡或 Windows/Linux/x86 验收。

已确定采用 llama.cpp Q4_0，Q8_0 仅保留为质量对照。排除本次 Q4_K_M 作为默认：它既未明显减小文件，又更慢。后续应收口现有 Elysia 服务管理私有原生子进程的合同，再开始一个 Issue、一个 PR 的产品接入。
